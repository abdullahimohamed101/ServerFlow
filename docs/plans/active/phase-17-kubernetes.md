## Outcome

`make k8s-up` creates a local `kind` cluster, loads the six Phase 16 images into it, applies a kustomize overlay and bootstraps tenants and keys; `make k8s-smoke` proves the system works end to end in the cluster with real requests; `make k8s-roll-test` replaces every gateway pod under sustained client load and reports the number of failed client requests, which must be zero, next to a negative control (drain grace removed) that must fail, so the measurement is shown able to see an outage. `make k8s-down` deletes the cluster and leaves nothing behind.

```text
host 127.0.0.1 only (kind extraPortMappings -> NodePort):  gateway :28080   control plane :29090   Prometheus :29091   Grafana :23000   Jaeger :26686
namespace serverflow  (Pod Security Admission: enforce=restricted;  NetworkPolicy: default deny + explicit allows)
  gateway x3  (Deployment, maxUnavailable 0, PDB)  --> control-plane x1 (Deployment, Recreate; registry is in memory)
      |  |  |                                              ^ register/heartbeat on localhost-sidecar, over the Service
      |  |  +--> postgres / redis / redpanda  (StatefulSets, 1 replica each, no HA)    usage-consumer --> postgres
      |  +-----> jaeger          prometheus (kubernetes_sd, namespaced Role) --> gateway :9100, control-plane :9101, mock workers :9000 --> grafana
      +--------> worker pods:  [ mock-worker :9000 ] + [ worker-agent (new loopback status port) ]   x3, Deployment, pod IP advertised
  Jobs: migrate, redpanda-init, bootstrap-tenants (run by scripts/k8s-up.sh in order)
```

Acceptance headline (spec §58): *Deploy, service, configmap/secret, readiness/liveness, resource limits; rolling gateway update with no outage.* "Measured" means a number from a run, with the denominator (D23).

## Non-Goals

- GPU workers, device plugins, vLLM, node labels, taints and affinity for GPUs (Phase 18). The pod shape chosen for mock workers (main container plus agent in one pod, readiness that includes registration, pod-IP advertisement) is the shape Phase 18 needs; nothing here assumes a CPU-only worker.
- Autoscaling (HPA, KEDA, queue-depth signals; Phase 19). Replica counts are fixed numbers.
- High availability of any stateful dependency, of the control plane, or a multi-node, multi-zone, or cloud claim. PostgreSQL, Redis and Redpanda are single in-cluster instances for development, with the same honesty caveats as Phase 16. The control plane keeps its registry in memory, so it has one replica; this is a limit of the code, not of the manifests.
- A real cloud load balancer, TLS termination, Ingress or Gateway API, cert-manager, service mesh. A `NodePort` Service reached through kind's loopback port mapping is the dev entry point (D13). An Ingress is described in the docs and not shipped.
- Helm, operators (CloudNativePG, Strimzi, Redpanda operator), the Prometheus operator and its CRDs (D1, D14, D8).
- Publishing images to a registry, signing, SBOMs (D5).
- Any change to scheduling, retry, rate-limit, auth, event or metric behaviour. The only code change is the worker agent's loopback status endpoint (D6, PR 1).
- Windows-native scripts (WSL2 is fine, as in Phase 16).

## Current Architecture (verified while planning, 2026-10-22)

- **Images** (Phase 16, `deploy/docker/Dockerfile`): `gateway`, `control-plane`, `worker-agent`, `mock-worker`, `usage-consumer`, `admin`; distroless static, user 65532, exec-form entrypoints (the Go process is PID 1 and handles SIGTERM), a `healthcheck` binary (loopback URLs only, HTTP 2xx) in each, no shell. Tags `serverflow/<name>:dev`, built locally, never pushed. Third-party images are pinned `tag@digest` in `docker-compose.yml` and come from `mirror.gcr.io` and `quay.io`; Docker Hub is avoided because it rate-limits shared runners, and `public.ecr.aws` stopped answering GitHub-hosted runners on 2026-10-16 (ADR-021).
- **Ports and probes today.** Gateway: data `:8080` with `/healthz` (always 200 while the process serves), `/readyz` (in registry mode 503 until the registry has a worker; 503 immediately on SIGTERM when resilience is on), both open even with API-key auth; metrics on a separate listener `:9100` (binary refuses a non-loopback metrics address without `SERVERFLOW_METRICS_TOKEN`). Control plane: API `:9090` (token-protected, `/healthz` open), metrics `:9101`. Mock worker: `--addr` (default loopback; flags only, **no env overlay**, but Kubernetes expands `$(VAR)` in `args`), `/readyz`, `/health`, `/metrics` on the service port, `--drain-announce`, `--drain-timeout`, `--startup-delay`. Usage consumer: `/healthz` and `/metrics` on `127.0.0.1:9103` (loopback is enforced, so only an exec probe can reach it). **Worker agent: no HTTP server at all**; it registers, heartbeats (2 s), reports `DRAINING` and deregisters, with an internal 5 s shutdown timeout.
- **Drain** (Phase 15 PR F, measured with processes on loopback only): on SIGTERM `/readyz` fails at once, responses carry `Connection: close`, the listener stays open for `resilience.drain.readiness_grace` (default `min(5s, shutdown_timeout/2)`), then it closes and in-flight requests finish within `gateway.shutdown_timeout` (default 30 s) of the signal, then the process exits non-zero. A second signal exits at once. **`resilience.mode` still defaults to `off`** on this master, and drain exists only with `on` plus `gateway.worker_source: registry`.
- **Registry.** Gateway default `registry_refresh` 1 s; agents heartbeat every 2 s; suspect 5 s, unhealthy ~11 s, lost ~31 s, retention 5 min. A worker ID registered twice makes the older agent exit (`ErrSuperseded`). `gateway.worker_networks` (CIDR list) restricts what the gateway will dial; empty allows any non-forbidden address and logs a WARN.
- **Secrets.** `scripts/dev-up.sh` `ensure_secrets` writes `.dev/{postgres,dsn,redis,kafka,controlplane,metrics,grafana}.env` (0600, directory 0700) from `/dev/urandom` and `.dev/metrics_token`; service names in the DSNs are `postgres`, `redis`, `redpanda`, `control-plane`, `jaeger`, `prometheus`. API keys are the one stdout line of `admin key create`, captured straight into a 0600 file.
- **Observability assets** reusable as is: `observability/prometheus/rules/*.yml` (and their promtool tests), the four dashboards (49 KB in total, far below the 1 MiB ConfigMap limit), Grafana provisioning with `${PROMETHEUS_URL}`. Job names (`serverflow-gateway`, `-control-plane`, `-mock-worker`) and the `worker_id` label (equal to the agent's ID) are what dashboards join on.
- **Nothing Kubernetes exists**: no `deploy/kubernetes`, no `kind`/`kubectl`/`helm`/`k3d`/`kustomize`/`kubeconform` on the development Mac (all checked absent). `ARCHITECTURE.md` says Phase 17 reuses the images.

### Facts about the development machine (checked 2026-10-22)

macOS arm64, 24 GB RAM, 663 GB free disk. Docker engine is Colima 0.10.3, profile `default`, **2 CPUs, 4 GiB RAM, 60 GiB disk**, Docker 29.5.2, no `buildx`. `docker system df` reports 26 GB of images, of which 22 GB reclaimable (other projects and old Phase 16 stages), 3 GB of volumes. A Phase 16 stack at rest used about 460 MiB (benchmark note) with limits summing to about 2.4 GB; a kind node adds an API server, etcd, kubelet and CoreDNS, which is expected to cost on the order of 1 GB (an estimate, measured in PR 2). So the current VM is **too small** for Kubernetes plus other work and D3 asks for a larger one.

## Decisions (confirm before implementation)

Decision numbers are stable identifiers, not reading order (D19 and D20 sit with the probes because they depend on them).

### Manifests, tooling and CI

- **D1. Plain YAML with kustomize: `deploy/kubernetes/{base,overlays/kind,kind}`; no Helm.** Spec §48 names `deploy/kubernetes (base/overlays)` and `helm`. Kustomize is built into `kubectl`, so it adds no tool beyond the one every Kubernetes workflow needs; the rendered output is plain YAML a reviewer can read and a Go test can parse; there is no template language to test. One overlay (`kind`) is the tested target. Config values that change per environment are patches, and ConfigMaps are generated with `configMapGenerator`, which appends a content hash to the name so changing a setting rolls the pods (this is also the clean way to trigger the rolling-update test). Rejected: **Helm** (another binary, a second language inside YAML, harder diffs, and no multi-environment need today; a chart can wrap the same base later, listed as future work), **raw `kubectl apply -f` of one big file** (no overlays, patches become copies), **Kustomize plus Jsonnet/cue** (dependency for no gain). Build-then-apply: kustomize's default load restrictor forbids referencing `observability/` (rules, dashboards, provisioning) from `deploy/kubernetes/`, and `kubectl apply -k` has no flag to relax it, so scripts and docs run `kubectl kustomize --load-restrictor=LoadRestrictionsNone deploy/kubernetes/overlays/kind | kubectl apply -f -`. Copying those files would create drift; this is the cost, named, and a test pins the command. Rendering needs `kubectl` of a pinned minor version.
- **D2. Local cluster: `kind`, one node, a dedicated kubeconfig and context.** Reasons: upstream-conformant Kubernetes (the same API server, kubelet, Pod Security Admission, kube-proxy and CoreDNS as managed clusters), a node is a container in the Docker the project already uses, a 30-line config file pins ports and pod CIDR, `kind load` gets local images in without a registry, and it is the common choice for CI on GitHub-hosted runners, so the laptop and CI run the same thing. Every script uses `--kubeconfig .dev/k8s/kubeconfig` and the context `kind-serverflow` and **refuses any other context**, so a later real cluster in `~/.kube/config` can never be touched by `make k8s-*` (tested). Rejected, with the deciding factor: **Colima's built-in k3s** (needs no extra tool except `kubectl`, but it means reconfiguring and restarting the user's only Docker VM, k3s differs from upstream in the control plane, and CI cannot reproduce it); **k3d** (lighter and its bundled kube-router does enforce NetworkPolicy, but k3s deviations and a second runtime to maintain; it is the named fallback if kind's default CNI turns out not to enforce NetworkPolicy and installing Calico is judged too heavy, D15); **minikube** (adds a VM or driver layer on macOS for no benefit). Open: the exact kind and node-image versions are resolved and pinned (`kindest/node:<tag>@sha256:<digest>`) in PR 2; the node image is mirrored on `mirror.gcr.io` only if an anonymous pull is shown to work, otherwise Docker Hub is used and its rate limit is a CI risk (Risks).
- **D3. Resources and what the user must approve.** Required installs (none performed by this plan): `kind` and `kubectl` through Homebrew (`brew install kind kubectl`: two static binaries, tens of MB each; `kubectl` within one minor of the node image). Recommended: `kubeconform` (`brew install kubeconform`, a small static binary) for the static job; if declined, the static job and a `make` target run its pinned container image instead, at the cost of one extra image pull. Not needed: `helm`, `kustomize` (inside `kubectl`), `k3d`, `minikube`. Disk: the kind node image is about 1 GB and, once the stack is loaded, containerd inside the node holds a second copy of every image (about 1.5-2.5 GB, mostly Redpanda, Grafana, Prometheus and the six ServerFlow images), so expect **3-5 GB of the Colima disk** while the cluster exists; `kind delete cluster` returns it. RAM: **the existing 4 GiB VM cannot hold a kind node and the stack**. Recommended: a **second Colima profile** that leaves the user's running `default` VM and its containers alone: `colima start --profile serverflow-k8s --cpu 4 --memory 8 --disk 40` (a separate Docker daemon with its own images, so the build for kind runs there too and the `default` profile's 22 GB of reclaimable images is not touched; it costs up to 8 GiB of the Mac's 24 GiB while running, and `colima stop -p serverflow-k8s` frees it). The alternative, resizing `default` (`colima stop && colima start --cpu 4 --memory 8`), restarts every container of every other project in that VM and is not recommended. All estimates are replaced by measured numbers in `docs/benchmarks/phase-17-kubernetes.md` (PR 2 and PR 6). Scripts print the Docker context in use and refuse to start when the engine reports under 4 GiB of memory or under 8 GB of free disk.
- **D4. Pre-commit-free static checks: kustomize build, `kubeconform`, and Go policy tests; no conftest/polaris/kube-score gate.** (a) `kubectl kustomize` must succeed for base and overlay (also catches missing generator files); (b) `kubeconform -strict -summary` against the schemas of the pinned Kubernetes minor (no CRDs are used, so no `-ignore-missing-schemas`; its default schema location is a GitHub raw URL, so the CI job pins a release binary by SHA-256 like `hadolint` and, if the schema fetch proves flaky, vendors the schema JSON for the kinds we use); (c) Go tests in `tests/k8s` parse the rendered YAML and assert the policy in D22. Go tests are chosen over Polaris or conftest because the repository already enforces compose policy that way (`tests/deploy`), they can compare against `docker-compose.yml` and `internal/config`, and they add no tool; optional extra scanners (kube-score, Polaris) may be run by a human and are not gates. (d) With a cluster, `kubectl apply --dry-run=server` and the real apply exercise admission, including Pod Security `restricted`, which is the strongest "is this hardened" check available and costs nothing.
- **D5. Images: reuse the six, load by tag, no registry in this phase.** `scripts/k8s-up.sh` builds with the existing Dockerfile (same pins, same `VERSION`/`COMMIT` stamping, serial builds to avoid the OOM seen in Phase 16) in the Docker daemon of the cluster's profile and runs `kind load docker-image serverflow/<name>:dev`. Manifests use `image: serverflow/<name>` with `imagePullPolicy: IfNotPresent` and the overlay's `images:` transformer is the single place to set a registry and a digest later. Third-party images are copied from the **digests already pinned in `docker-compose.yml`** and a test fails if the two files disagree (one set of pins, one Dependabot procedure). The nodes pull third-party images themselves (kubelet retries `ImagePullBackOff` with backoff, which is free pull retrying); they are not pre-loaded, because `kind load` of a multi-platform image into containerd is known to be fragile (index versus single-platform digest, containerd image store), and digest-pinned references would then fail to match; PR 2 measures it and records the verdict. Registry decision for Phase 17: **none**; publishing (GHCR, tags, digests, signing, multi-arch) is deferred until something other than a developer's laptop consumes the images, because every candidate (GHCR with `GITHUB_TOKEN`, a registry on ECR/GCR) adds credentials and a retention policy that nothing here exercises. What a real deployment would do: build once in CI, push by digest, reference by digest in the overlay, scan and sign.
- **D6. Worker agent liveness and readiness: add a loopback status endpoint (code change, PR 1).** Today the agent has no HTTP server, so Kubernetes could only observe "process exists". A hung heartbeat loop, or an agent that never registered, would leave a Ready pod and a silently missing worker. Add to `cmd/worker-agent` a listener on `127.0.0.1:9102` (key `worker.status_listen`, env `SERVERFLOW_WORKER_STATUS_LISTEN`, default empty = off, so existing behaviour is unchanged; loopback enforced like the consumer's `metrics_addr`) serving `GET /healthz` (200 while the heartbeat loop ticked within `3 x heartbeat_interval`; it does **not** depend on the control plane being reachable, so a control-plane outage cannot make Kubernetes restart every agent) and `GET /readyz` (200 only when the agent is registered and the last heartbeat was accepted within `unhealthy_timeout`, and the backend probe passes). In the pod these are **exec probes running the existing `healthcheck` binary against `127.0.0.1:9102`** (kubelet's httpGet targets the pod IP, which a loopback listener does not answer), which is what Phase 16 D29 anticipated, and nothing new is exposed on the pod network. The same listener lets Compose finally enable the agent's healthcheck (Phase 16 had to disable it). Pod readiness is then "mock-worker `/readyz` and agent `/readyz`": a rolling update of workers keeps the old pod until the new one is **registered**, not merely running (spec §39). Rejected: a heartbeat marker file plus an exec test (needs an agent change as well, an emptyDir, and says less); no probe for the agent (the gap above); agent as a separate Deployment (D7). Security-sensitive in the sense of AGENTS.md only because it adds a listener; the review checks loopback enforcement and that no token or registry data is served.
- **D7. Worker pod shape: one pod per worker with the agent as a second regular container (a sidecar), pod IP advertised.** The pod runs `mock-worker` (listening `0.0.0.0:9000`, `--worker-id=$(POD_NAME)` through Kubernetes' `$(VAR)` argument expansion, so no shell and no new flag) and `worker-agent` with `SERVERFLOW_WORKER_ID=$(POD_NAME)`, `SERVERFLOW_WORKER_BACKEND_URL=http://127.0.0.1:9000` (localhost: no network hop between agent and backend, nothing to resolve) and `SERVERFLOW_WORKER_ADVERTISE_URL=http://$(POD_IP):9000` (the address the gateway dials; `POD_NAME` and `POD_IP` come from the downward API). Reasons: the agent and the backend share a fate (a pod that dies deregisters one thing, no ghost registration), registration waits for the same readiness, and Phase 18's vLLM pod is the same shape. Worker ID = pod name, unique per pod, so a replaced pod never collides with its predecessor (`ErrSuperseded`); a pod killed hard leaves its old ID `suspect`, `unhealthy`, then `lost` and expired by `retention`, as in Compose. Rejected: **a separate agent Deployment** (needs discovery of the backend, a different failure domain and lifecycle, supersede races on replacement); **a StatefulSet** (stable IDs we do not need; Deployments are the autoscaling shape and spec §37 puts a Deployment per model). Native sidecar containers (`initContainers` with `restartPolicy: Always`, GA in recent Kubernetes) are not used: they order start and stop, but the drain contract in `resilience.md` ("signal the agent first or the backend first; both end deregistered") already holds with concurrent SIGTERM, and the PR 6 worker roll test measures it. Revisit if that test shows a gap.
- **D8. Workers: one Deployment `mock-worker`, 3 replicas, identical speed.** Phase 16 had three workers of 100/60/20 tokens/s; reproducing that needs three near-identical Deployments. The default is one Deployment (spec §37's "Deployment per model", the shape Phase 19 scales) with the Phase 16 middle speed; the heterogeneous trio is available as an optional kustomize component `components/heterogeneous-workers` (three Deployments) if the user wants scheduler comparisons in the cluster (Open decision 6). Mock worker concurrency and queue are as in Phase 16 (8 and 64).
- **D9. Secrets: generated like `dev-up.sh`, delivered as Kubernetes Secrets, never in git, never printed.** `scripts/dev-up.sh` gains a `secrets` subcommand that only calls the existing `ensure_secrets` (no behaviour change; the Compose path is unchanged and tested), so both stacks use one generator and the same `.dev/*.env` files (the service names in the DSNs are identical on purpose). `scripts/k8s-up.sh` creates the Secrets with `kubectl create secret generic <name> --from-env-file=.dev/<name>.env --dry-run=client -o yaml | kubectl apply -f -` (values never appear on a command line; the YAML goes through a pipe, not a file), one Secret per concern as in Phase 16 so a pod receives only what it needs (`envFrom.secretRef`); the Prometheus token is a **file volume** with `defaultMode: 0440` and `fsGroup`, which replaces Phase 16's world-readable `metrics_token` workaround. API keys and the kubeconfig live in `.dev/k8s/` (0700, gitignored; separate from Compose's `.dev/api_key`, because a key is valid only in the database that issued it). No Secret, and no secret-looking value, is in any file under `deploy/kubernetes/` (`TestNoSecretsCommitted` extended). Documented honestly: Secrets are base64, not encrypted, in the kind cluster's etcd; anyone with `kubectl` access to the namespace can read them (same trust boundary as Phase 16's Docker socket). A real deployment would use encryption at rest, an external secret store (cloud secret manager through External Secrets or the CSI driver), RBAC that denies `get secrets`, and rotation; none of that is built or claimed. The bootstrap of tenants and keys runs `admin key create` in a one-off pod attached with `kubectl run --rm -i --restart=Never` and its single stdout line goes straight into a 0600 file; the kubelet still writes the container log on the node until the pod is deleted by `--rm`, which is a residual leak window inside a throwaway cluster, and the verifier searches the node logs after (Risks).
- **D10. Stateful dependencies: single-instance StatefulSets, honest.** PostgreSQL 16 and Redpanda each get a StatefulSet (1 replica), a headless-compatible ClusterIP Service named as in Compose (`postgres`, `redpanda`) and a small PVC from kind's default `standard` StorageClass (local path, node-local; deleted with the cluster); Redis is a StatefulSet with an `emptyDir` (its counters are rebuildable and Phase 16 ran it with persistence off). Compared with Phase 16's all-tmpfs default, a PVC means a restarted pod keeps its keys and topic, which in Kubernetes is the common case rather than an operator action (probe failures, node pressure, rollouts), while `kind delete cluster` still leaves nothing. Hardening follows Phase 16 recipes translated to `securityContext`: PostgreSQL `runAsUser/fsGroup 70`, Redis `999:1000`, Redpanda `101` with `emptyDir` on `/etc/redpanda` and `/var/lib/redpanda/.config`, all `readOnlyRootFilesystem`, `drop: [ALL]`, `allowPrivilegeEscalation: false`, `seccompProfile: RuntimeDefault`, so the namespace can enforce Pod Security `restricted`. Redpanda keeps `--advertise-kafka-addr=internal://redpanda:9092` (the Service name; valid for one broker, the multi-broker form is not attempted). Redis' password reaches the server through a file written to the `emptyDir` by the same `sh -c` wrapper Compose uses (not argv). Rejected: operators and Bitnami-style charts (moving images, heavy CRDs, HA we do not claim), `Deployment`s for state (identity and PVC semantics are what StatefulSet is for), HostPath volumes (blocked by `restricted`).
- **D11. Control plane, gateway, consumer.** Control plane: `Deployment`, **1 replica, `strategy: Recreate`**, because two instances would hold two divergent in-memory registries (agents register through the Service to whichever answers). A restart makes the registry empty until agents re-register; the gateway keeps its last view for `registry_max_staleness`; the PR 6 observation (not a gate) records what clients see during a control-plane restart, and the docs state that a control-plane restart is not zero-impact. Gateway: `Deployment`, 3 replicas in the overlay (base 2; one replica cannot roll without an outage), `RollingUpdate` with `maxUnavailable: 0`, `maxSurge: 1`, `minReadySeconds: 5`, `progressDeadlineSeconds: 120`, a `PodDisruptionBudget` (`maxUnavailable: 1`), `topologySpreadConstraints` and anti-affinity as **preferred** only (single node; multi-node scheduling is not verifiable, see Not Verifiable). `SERVERFLOW_GATEWAY_WORKER_NETWORKS` is the pod CIDR (`10.244.0.0/16`, pinned in the kind config's `networking.podSubnet`, patched per cluster), which closes ADR-021's open item for this deployment. Usage consumer: `Deployment`, 1 replica, exec probe `healthcheck http://127.0.0.1:9103/healthz`. The `Service` objects are `ClusterIP` with the Compose names; `automountServiceAccountToken: false` everywhere except Prometheus.
- **D12. Gateway configuration is explicit, including the settings the drain depends on.** From Compose, translated one-to-one (a test compares each `SERVERFLOW_*` name with `internal/config`'s overlay, reusing `TestEnvVariablesAreHonoured`'s approach): registry worker source, `control_plane_url`, `CONTROL_PLANE_ALLOW_INSECURE_TRANSPORT=true` (W1, ADR-021: the token crosses the cluster network in plain HTTP; D17), metrics on `0.0.0.0:9100` with the token, `AUTH_MODE=required`, rate limits and events on, tracing on with `TRACING_ALLOW_INSECURE_TRANSPORT`. New for Kubernetes and set explicitly rather than relying on defaults: `SERVERFLOW_RESILIENCE_MODE=on` (**the shipped default is `off` until Phase 15 PR G; without it there is no drain, which is the whole point of the rolling-update claim**), `SERVERFLOW_RESILIENCE_DRAIN_READINESS_GRACE=5s`, `SERVERFLOW_GATEWAY_SHUTDOWN_TIMEOUT=30s`. A static test fails if the gateway manifest lacks the first, if `grace >= shutdown_timeout`, or if `terminationGracePeriodSeconds < shutdown_timeout + 10s` (D19).

### Probes, drain, rolling update

- **D13. Probe map (all timings are the defaults to start with; PR 6 can tune them with evidence).**

  | Pod / container | startupProbe | readinessProbe | livenessProbe |
  | --- | --- | --- | --- |
  | gateway | `httpGet /healthz :8080`, period 1 s, failureThreshold 30 | `httpGet /readyz :8080`, period 2 s, timeout 2 s, failureThreshold 2 | `httpGet /healthz :8080`, period 10 s, failureThreshold 3 |
  | control-plane | `httpGet /healthz :9090`, 1 s x 20 | `httpGet /healthz :9090`, period 2 s | `httpGet /healthz :9090`, period 10 s |
  | mock-worker (in worker pod) | `httpGet /readyz :9000`, 1 s x 30 | `httpGet /readyz :9000`, period 2 s | `httpGet /health :9000`, period 10 s |
  | worker-agent (in worker pod) | exec `healthcheck http://127.0.0.1:9102/healthz`, 1 s x 20 | exec `healthcheck http://127.0.0.1:9102/readyz`, period 2 s | exec `healthcheck .../healthz`, period 10 s |
  | usage-consumer | none | exec `healthcheck http://127.0.0.1:9103/healthz` | same, period 10 s |
  | postgres / redis / redpanda | `pg_isready -h 127.0.0.1` / `redis-cli ping` / `rpk cluster health` (exec, as in Compose) | same command | same command, period 20 s, failureThreshold 6 |
  | prometheus / grafana / jaeger | `httpGet` on their ready/health/UI paths | same | same, lenient |

  Rules, enforced by a test: **liveness never depends on another service** (the gateway's liveness is `/healthz`, never `/readyz`, because `/readyz` depends on workers existing; a worker outage must not restart gateways); every long-running container has a readiness probe; startup probes absorb slow starts so liveness can stay short. Trade-off stated and open (Open decision 4): the gateway's readiness is `/readyz`, so if every worker is gone all gateways become NotReady, the Service has no endpoints, and clients see connection errors from the node instead of the gateway's JSON `503 NO_CAPACITY`. Using `/healthz` for readiness would keep the honest error but would send traffic to a new pod before its registry view is loaded and would hide the drain signal from the probe path. Default: `/readyz` (spec §39: Running is not Ready; the drain contract is written against it), with the effect documented and measured in the control-plane/worker-loss observation of PR 6.
- **D19. The drain timeline and the numbers that must satisfy it.** Settings: no `preStop` hook, `readiness_grace` = 5 s, `shutdown_timeout` = 30 s, **`terminationGracePeriodSeconds` = 45 s** for the gateway. Why no `preStop`: the gateway already implements the wait inside its own signal handling and tests it; the usual `preStop: sleep` workaround would be a second, untested copy of the same wait, and the image has no `sleep` (distroless; Kubernetes' native `sleep` hook action would work in recent versions and is the documented fallback if PR 6 shows the grace is not enough). Timeline for a pod replaced by a rolling update (t = the API server sets `deletionTimestamp`; the new pod was already Ready because of `maxSurge`):

  | t | Kubernetes | gateway |
  | --- | --- | --- |
  | 0 | EndpointSlice marks the pod `terminating` and not ready (this happens for any deleted pod, not via the readiness probe, so the probe period does not delay it); kube-proxy on each node rewrites its rules on its next sync (typically 1-2 s, to be measured); the kubelet sends SIGTERM at once (no preStop) | `/readyz` 503, `Connection: close` on every later response, `gateway_draining 1`, still serving, queue still open |
  | 0 - 5 s | rules converge; established keep-alive connections receive `Connection: close` on their next response and reconnect to other pods | listener open for the grace; new connections that still arrive from stale rules are served |
  | 5 s | | queue closes, listener closes, in-flight requests and streams run on |
  | up to 30 s | | in-flight finishes; whatever remains at 30 s after the signal is cut and the process exits 1 |
  | 45 s | the kubelet sends SIGKILL if the container is still alive | |

  Constraints (all asserted by static tests and checked by PR 6): `grace` > measured propagation time with margin (PR 6 records, per replaced pod, the time from SIGTERM to the last request that pod accepted; the benchmark note reports max and p99); `grace` < `shutdown_timeout`; `TGPS` >= `shutdown_timeout` + 10 s; the longest stream in the test is shorter than `shutdown_timeout - grace` (25 s; the mock streams are about 2-4 s). For worker pods: mock-worker `--drain-announce=6s` (must exceed heartbeat 2 s + registry refresh 1 s + margin, `resilience.md`), `--drain-timeout=30s`, `terminationGracePeriodSeconds: 45`; the agent's own 5 s shutdown timeout covers deregistering.
- **D20. The rolling-update test is a measurement with a control.** `make k8s-roll-test` (PR 6): (1) wait until the stack is smoke-green; (2) start a closed-loop load of 24 concurrent clients through the host entry point `http://127.0.0.1:28080` (kind port mapping, node, kube-proxy, pod: the full path including connection reuse; a mix of non-streaming and streaming requests, half the clients keep-alive and half opening a connection per request) using an API key of a generous tenant, **no client-side retries**; (3) after a 20 s baseline, apply a config change that rolls the gateway (the generated ConfigMap hash changes) and a second change of the image tag annotation, waiting for `kubectl rollout status` each time, so all three pods are replaced twice; (4) keep the load running 20 s after; (5) report total requests, the number of failed requests by class (connection refused/reset, timeout, 5xx with its error code, truncated stream, malformed SSE), the rollout duration, and per replaced pod the SIGTERM-to-last-request time. **Pass = zero failed requests of any class, with at least 3,000 requests during the rollouts** (zero of 3,000 bounds the true failure rate below about 0.1% at 95% confidence, the "rule of three"; the report prints that bound instead of "no failures, therefore no outage"). (6) **Negative control** in the same command: repeat with `SERVERFLOW_RESILIENCE_DRAIN_READINESS_GRACE=0` and resilience off for a run (the Phase 15 "feature off" path), which is expected to produce failures; if it produces none, the test is declared unable to see the outage and the command fails. (7) Optional observation runs, recorded and not gating: `kubectl delete pod` of a gateway under load; a rollout to an image that never becomes ready (`progressDeadlineSeconds` stalls, old pods keep serving, zero failures, then `rollout undo`); a worker rolling restart (Phase 15's `rollWorkers` equivalent: expected zero failures and zero retries with the 6 s announce); a control-plane restart (observe only). The load generator lives in `tests/k8s/e2e` and reuses `internal/bench` primitives where they fit (a `benchmark run --target` run counts failures only as a percentage and treats up to 5% as valid, which is too coarse; the plan is to read `internal/bench/driver` first and write the smallest client that records per-request status with timestamps), uses only the standard library HTTP client, and prints no key.

### Network, security, observability, entry

- **D14. Metrics scraping: plain Prometheus with `kubernetes_sd_configs` (role `pod`), no ServiceMonitor.** `ServiceMonitor` and `PodMonitor` are Prometheus-operator CRDs; using them would add the operator and its CRDs to every cluster, make the static job need CRD schemas, and could not be tested without installing the operator in kind. A `ConfigMap` holds `observability/k8s/prometheus.yml` with the **same job names, `sample_limit`, `rule_files` and `global`** as the other two configs (a drift test extends `TestPrometheusComposeMatchesLocal`), pod selection by the labels `app.kubernetes.io/part-of=serverflow` and `app.kubernetes.io/component`, the metrics port picked by **container port name** (`metrics`), and `worker_id` relabelled from `__meta_kubernetes_pod_name`, which equals the agent's ID by D7, so worker-side and registry-side series still join. Gateway and control-plane jobs present the bearer token from the mounted file. Permissions: a `Role`/`RoleBinding` in the namespace granting only `get/list/watch` on `pods` to Prometheus' ServiceAccount (the only workload with a mounted API token). Rules, dashboards and Grafana provisioning are mounted from ConfigMaps built from the existing files. Rejected: static targets (pod IPs change on every rollout), `dns_sd` on a headless Service (no `worker_id` label), annotations-based discovery (a convention that nothing enforces). Revisit when a cluster already runs the operator; then a `ServiceMonitor` component is additive.
- **D15. Entry: `NodePort` Services bound to loopback by kind, no Ingress.** The kind config maps host `127.0.0.1:28080/29090/29091/23000/26686` to fixed NodePorts (gateway, control plane, Prometheus, Grafana, Jaeger) using `listenAddress: "127.0.0.1"`; the host ports differ from Compose's (18080 and friends) so both stacks can run at once if RAM allows, and the same pre-flight port check as Phase 16 names the variable to change. The control plane is published only because the benchmark tool and operators use it from the host, token-protected, as in Phase 16, and `K8S_CONTROL_PLANE_PORT=` empty removes it. Ingress or a `LoadBalancer` Service are not shipped: kind has no LB implementation, an Ingress needs a controller whose choice is outside this phase, and neither can be verified here with the properties that matter (cloud LB health checks, deregistration delay, TLS). The docs include a reviewed example of the Ingress/Gateway API objects and `externalTrafficPolicy: Local` guidance, labelled untested.
- **D16. Network policy: default deny (ingress and egress) plus an allow list written from the Compose topology; enforcement is verified, not assumed.** Allows: from anywhere to `gateway:8080` (node-port traffic arrives from the node); gateway to control plane `9090`, PostgreSQL `5432`, Redis `6379`, Redpanda `9092`, Jaeger `4318`, and worker pods `9000`; agents to control plane `9090`; consumer to PostgreSQL and Redpanda; Prometheus to gateway `9100`, control plane `9101` and workers `9000`; Grafana to Prometheus `9090`; Grafana, Prometheus, Jaeger, control-plane from the node for published NodePorts; every pod to CoreDNS (UDP/TCP 53); nothing to the internet. Kubelet probes must still succeed (the CNI must always allow node-to-pod traffic; PR 5 checks that probes stay green). **Unknown to settle in PR 5:** whether kind's default CNI (kindnet) enforces NetworkPolicy in the pinned release. The check is a deny test (a throwaway pod labelled as the gateway's neighbour reaches Redis and a pod without the label does not). If it enforces, the runtime test is a gate; if not, the policies are still written and statically tested, the docs say they are not enforced locally, and the options are installing Calico/Cilium into kind (extra images, minutes of start-up, a documented opt-in `K8S_CNI=calico`) or using k3d for this one check (Open decision 7). Default: write policies in PR 5, test enforcement, then decide with the numbers.
- **D17. Security context and what is deliberately weaker than production.** Every pod: namespace labels `pod-security.kubernetes.io/enforce=restricted` (and `audit`/`warn`), `runAsNonRoot`, explicit numeric `runAsUser`, `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true` (writable paths are `emptyDir` with `sizeLimit`), `capabilities.drop: [ALL]`, `seccompProfile: RuntimeDefault`, `automountServiceAccountToken: false` (except Prometheus), no `hostNetwork/hostPID/hostPath/privileged`, `shareProcessNamespace` unset, per-workload ServiceAccounts. The control-plane token still crosses the cluster network in plain HTTP (W1 / ADR-021): NetworkPolicy narrows who can reach the control plane, but pod-to-pod traffic is unencrypted and unauthenticated at the network layer; a service mesh (mTLS) or TLS in the Go clients is the production answer and is listed as a Phase 17 gap, not built. No TLS externally (no ingress). Secrets as D9. Image pull is `IfNotPresent` from local loads; no `imagePullSecrets`.
- **D18. Resources.** Every container has `requests` and a memory `limit` (limits from Phase 16's `mem_limit` table: gateway 128 Mi, control plane 64, agent 32, mock worker 64, consumer 64, PostgreSQL 256, Redis 64, Redpanda 768, Prometheus 256, Grafana 256, Jaeger 256; requests at 50-70% of the limit so the scheduler packs honestly), CPU requests of 50-250m, **no CPU limits** on the request path (CFS throttling shows up as latency; Go 1.25+ already sizes `GOMAXPROCS` from the cgroup, and the images build with 1.27), `GOMEMLIMIT` at about 80% of the memory limit as in Phase 16. QoS is Burstable by design. No `LimitRange`/`ResourceQuota` (YAGNI for one namespace; listed). Totals are computed by the static test and compared with the VM size recorded in D3.
- **D21. Namespace, naming, labels.** Namespace `serverflow` (spec §37); recommended labels `app.kubernetes.io/{name,component,part-of}` on everything, used by selectors, NetworkPolicies and Prometheus; Service names equal Compose names so DSNs, env files and Grafana's `PROMETHEUS_URL` are reused unchanged.

### Workflow, tests, CI

- **D22. Commands and files.** `scripts/k8s-up.sh` (`up | down | reset | status | smoke | roll-test | audit | --check-env`) with Makefile aliases `k8s-up`, `k8s-down` (deletes the cluster), `k8s-reset` (also `.dev/k8s/` and the `serverflow/*:dev` images of the profile), `k8s-smoke`, `k8s-roll-test`, `k8s-audit`, `k8s-render` (prints the rendered manifests with no Secret content, safe to paste), `k8s-check` (the static checks, no cluster). `up` is idempotent and phased, because Kubernetes has no `depends_on`: preflight (tools, versions, Docker context and memory, ports) -> `ensure_secrets` -> create the cluster (config pinned by D2) -> build and load the six images -> apply namespace, RBAC, Secrets and the data tier -> wait ready -> `migrate` Job -> `redpanda-init` Job -> apply the rest -> `kubectl wait` for every Deployment -> bootstrap tenants `dev` and `limited` and write their keys. Waits are `kubectl wait --timeout` with a printed cause (events and the last 20 log lines of the failing pod, secret-free) on timeout. `.env` handling reuses `dev-up.sh`'s hostile-input validator for the K8S_* variables (ports, cluster name) instead of a new parser. Static policy tests (`tests/k8s`, no cluster; need `kubectl` to render, so the CI job installs it and the gate fails if they did not run): hardening of every pod spec; probes per D13; resources per D18; labels and selectors line up, Service `targetPort` names exist; no `latest`, no unpinned third-party image, third-party digests equal Compose's; no `hostPath`/`hostNetwork`; Pod Security labels on the namespace; NetworkPolicy default deny and one allow rule for each edge in an edge table kept in the test; the gateway timing relations of D12/D19; rollout strategy, replicas and PDB of the gateway; no `NodePort` outside the overlay and kind mappings only on `127.0.0.1`; every `SERVERFLOW_*` name accepted by `internal/config`; no secret-looking literal in any manifest or ConfigMap; Prometheus job names and rule files equal the host and Compose configs; `k8s-*` scripts refuse a foreign kube context.
- **D23. Cluster smoke (`k8s-smoke`).** The Phase 16 smoke minus what does not apply, each check `PASS/FAIL/SKIPPED` and the same last-line contract (`smoke: N of N checks passed, 0 failed, 0 skipped`): K1 every pod Ready and zero restarts; K2 gateway `/readyz` 200 and `/v1/models` lists `mock-model` through the node port; K3 no key and bad key are 401; K4 non-streaming completion; K5 streaming completion ends with `[DONE]`; K6 requests reach three distinct workers (`scheduler_selections_total`); K7 the `limited` tenant gets 429 with `Retry-After`; K8 Prometheus reports gateway (all replicas), control plane and workers `up` and `inference_requests_total` is non-zero; K9 Grafana healthy with four dashboards; K10 usage rows appear (Redpanda -> consumer -> PostgreSQL); K11 a Jaeger trace holds gateway and mock-worker spans; K12 `kubectl delete pod` of one worker: it leaves the pool, requests stay 200, the replacement registers; K13 no generated secret appears in any pod log, `kubectl get -o yaml` of any non-Secret object, event, or in the node's container logs (searched, never printed); K14 quota shared across the three gateways (at most quota plus burst admitted over all replicas, S13's check). The load generator and checks never print a key or token.
- **D24. CI.** Two new jobs. (a) `k8s static (render, schema, policy)` on every pull request: no cluster, no pulls beyond a pinned `kubeconform` release (SHA-256 verified like `hadolint`) and `kubectl` from the runner image (its version is printed and compared with the pinned minor; mismatch fails with the instruction), the `tests/k8s` policy tests that **must run**, `scripts/check-yaml.py`, `shellcheck`; about 1-2 min. (b) `k8s smoke (advisory)`: kind via a pinned release binary (checksum-verified; `helm/kind-action` is an alternative if it keeps its actions pinned by SHA like the other workflows), a Docker build of the six images with the runner's BuildKit, `kind load`, the same `scripts/k8s-up.sh up` and `k8s-smoke`, logs and `kubectl describe`/events uploaded on failure through the same secret-withholding grep Phase 16 uses, cluster deleted `if: always()`. Estimated 10-15 min on a 4-vCPU runner (kind create 1-2 min, build about 1.5 min, loading about 1 min, node pulls of Redpanda, Grafana, Prometheus, PostgreSQL, Redis, Jaeger a few minutes, rollout and smoke 3-4 min; **an estimate, measured in PR 3**), budget 30 min. Triggers: pull requests that touch `deploy/kubernetes/**`, `scripts/k8s-up.sh`, `scripts/dev-up.sh`, `cmd/**`, `internal/config/**`, `deploy/docker/**`, `observability/**`, plus every push to master and the nightly workflow (path filtering is acceptable because the job is advisory; if it is ever made required, wrap it so it always reports). The rolling-update test runs in the nightly workflow and on manual dispatch, plus on pull requests that touch `deploy/kubernetes/base/gateway*` or the drain code (`internal/gateway/resilience*.go`), because it adds about 5-6 minutes. Registry limits: node image and third-party images are pulled by containerd inside kind with kubelet's own retry/backoff; the node image reference prefers `mirror.gcr.io` if shown to work (D2); Docker Hub is not used for anything else; `scripts/dev-pull.sh` is reused for the images the Docker daemon itself must have. The existing lesson stands: no CI job may depend on an unpinned or Docker Hub image it cannot retry. Advisory first, proposed as required after ten consecutive green runs on master (owner decision, `docs/development/ci.md`).
- **D25. Documentation.** `docs/operations/kubernetes-deployment.md` (topology, commands, ports, the drain timeline D19 with the measured numbers, probe map, secrets, NetworkPolicy, what is and is not hardened, troubleshooting: kind needs more memory than the default Colima VM, node image pulls, `ImagePullBackOff` for a not-loaded image, stuck rollouts, NetworkPolicy blocking, cleaning up), `docs/decisions/ADR-022-kubernetes-deployment.md` (D1, D2, D6, D7, D9, D10, D11, D14, D16, D17, D19; ADR-020 is Phase 15's and ADR-021 Phase 16's), `docs/benchmarks/phase-17-kubernetes.md` (every measured number: install sizes, cold and warm `k8s-up`, memory and disk, propagation and drain times, the rolling-update runs with denominators and the negative control), updates to `docs/operations/{docker-deployment,resilience,observability}.md` (the "Phase 17 will decide" sentences become links; `resilience.md`'s "Kubernetes preStop and termination grace periods ... not tested" line is replaced by what was tested), `docs/development/ci.md`, `ARCHITECTURE.md` and the README phase table.

## Acceptance Criteria

1. **From a prepared machine:** with the tools and the Colima profile of D3 present, `make k8s-up` exits 0 and `make k8s-smoke` exits 0 with the last line `smoke: N of N checks passed, 0 failed, 0 skipped`; the verifier follows only the docs.
2. **Reuse:** the same six images, built from the unchanged Dockerfile, are the only ServerFlow images in the cluster; third-party digests equal those in `docker-compose.yml` (test).
3. **Admission:** the namespace enforces Pod Security `restricted` and every pod is admitted; `make k8s-audit` lists, per container, user, `readOnlyRootFilesystem`, dropped capabilities, `allowPrivilegeEscalation`, seccomp, requests and limits, and finds no exception; no pod mounts a ServiceAccount token except Prometheus.
4. **Probes:** each container has the probes of D13; killing the gateway's workers (scale `mock-worker` to 0) makes gateways NotReady but never restarts them (liveness independent of dependencies); killing the worker agent process in a worker pod makes that pod NotReady, and its registration disappears; a deliberately failing readiness path in a new gateway version stalls the rollout (`progressDeadlineSeconds`) while old pods keep serving with zero failures.
5. **Resources:** every container has requests and a memory limit; the sum of limits is printed and below the VM's memory; no OOM kill or restart during `k8s-smoke` and a 60 s load at concurrency 12 (restart counts read from the API).
6. **Rolling update with no outage (D20):** the measured run reports at least 3,000 client requests across two full replacements of all gateway pods, **zero** failed requests of every class, per-pod drain timings, and the rollout durations; the negative control (grace 0, resilience off) produces at least one failure, else the test fails.
7. **Worker roll:** replacing every worker pod under load (`kubectl rollout restart`) costs the clients zero failures; the report states retries seen (`inference_retries_total`) and workers' deregistration.
8. **Secrets:** a scan of the repository diff, `kubectl kustomize` output, every non-Secret object (`kubectl get -o yaml`), all events, all pod logs, and the node's container logs and image layers finds none of the generated values (searched, never printed); secrets exist only under `.dev/` (0600/0700) and in-cluster Secret objects; `TestNoSecretsCommitted` covers `deploy/kubernetes/`; the bootstrap's key never appears in the shell output.
9. **Network policy:** default deny exists and every allowed edge has a table entry; either an enforcement test passes (a disallowed connection from a labelled test pod fails, an allowed one works, probes stay green) or the docs and the PR say plainly that the local CNI does not enforce them.
10. **Metrics:** Prometheus (plain `kubernetes_sd`, namespaced Role) shows all gateway replicas, the control plane and every worker `up` with `worker_id` equal to the pod name; `quality.sh observability` still passes unchanged for the host config; the dashboards load with zero provisioning errors and panels show data after the smoke.
11. **Stateful honesty:** restarting the PostgreSQL and Redpanda pods keeps keys and the lifecycle topic (PVC), restarting Redis resets counters; `kubectl delete` of the cluster leaves no container, volume or kubeconfig entry; the docs list what is lost on each.
12. **Safety of the scripts:** with a second kube context present and current, `make k8s-*` refuse to run against it (tested); the scripts need no network access beyond image pulls and make no change outside `.dev/k8s/`, the cluster, and Docker objects labelled for this project.
13. **Agent status endpoint (PR 1):** default off and loopback-only; `/healthz` and `/readyz` behave as in D6 under unit tests (loop stalled, not registered, control plane down: healthz stays 200, readyz 503); the Compose stack now has an agent healthcheck and `make dev-up && make dev-smoke` still end `0 failed`.
14. **Static gates:** `kubectl kustomize` renders base and overlay; `kubeconform -strict` passes; `tests/k8s` passes and the CI gate fails if any named test did not run; `go vet`, `gofmt`, `golangci-lint`, `go test -race ./...` pass; `scripts/quality.sh full` passes.
15. **CI:** the static job and the kind smoke job have run green on GitHub on the pull request that introduced them, with the smoke's final line recorded; a deliberately broken readiness path makes the job fail (checked once, recorded). Not verifiable before pushing; said so in the PR.
16. **Measured numbers** in `docs/benchmarks/phase-17-kubernetes.md`: installed sizes, cold and warm `k8s-up`, node memory, Colima disk before and after, the CI job time against the 30-minute budget.
17. **Host workflow unchanged:** with no cluster, `go test ./...`, `make dev-up` and `make dev-cluster` behave as before.

## Verification Plan

- **Without a cluster (CI static job, `make k8s-check`):** `kubectl kustomize` for base and overlay; `kubeconform -strict`; `tests/k8s` policy tests; the agent endpoint unit and race tests; YAML parse (`scripts/check-yaml.py`); shellcheck; the drift tests against `docker-compose.yml`, `internal/config`, and the Prometheus configs.
- **With kind:** `k8s-up`, `k8s-smoke` (K1-K14), `k8s-audit`, the NetworkPolicy enforcement test (D16), the rolling-update measurement with its negative control (D20), the worker roll, the observation runs, the secrets hunt, and the clean-delete check. Every wait is a poll with a deadline.

## Risks

- **Memory and disk on the development Mac.** The default Colima VM has 4 GiB and 60 GiB with 22 GB of reclaimable images already; a kind node plus the stack will not fit comfortably (estimate, measured in PR 2). Mitigation: the separate Colima profile (D3), pre-flight checks that refuse to start below 4 GiB or 8 GB free, `k8s-down`/`k8s-reset` that remove only this project's objects, and the Phase 16 lesson on dangling build stages (label-scoped prune). A runaway build already filled this VM once.
- **Image loading and digest pins.** `kind load docker-image` has failed on multi-platform images with the containerd image store (Docker 29 here), and a digest-pinned reference needs the node to hold that index. Mitigation: only the six locally built single-platform images are loaded; third-party images are pulled by the node; if loading fails the fallback is `docker save` plus `kind load image-archive`, then a local registry on the kind network; PR 2 records which works.
- **Registry rate limits in CI.** The `kindest/node` image and the third-party images are pulled on the runner; Phase 16 hit Docker Hub and ECR limits. Mitigation: mirror.gcr.io where an anonymous pull works (verified in PR 2, not assumed), kubelet's pull retry, an image-tarball cache for the heaviest image (Redpanda) as in Phase 16, the job advisory. A cold pull from a GitHub runner is unverified.
- **Readiness grace versus the real world.** 5 s is enough only if endpoint propagation and the front load balancer converge within it. In kind, kube-proxy is the whole path; behind a cloud LB the deregistration delay can be tens of seconds. The measured claim is for the kind topology only and is worded that way. A larger grace costs rollout time, not correctness.
- **NetworkPolicy may not be enforced locally** (D16): then the policy objects are untested at runtime, and a typo in an allow rule would be discovered only in a cluster that enforces them. Mitigation: the edge-table test, a CNI that enforces if the cost is acceptable, and plain wording in the docs.
- **Plain-HTTP control-plane token** (W1/ADR-021) persists in Kubernetes. NetworkPolicy and the namespace boundary reduce exposure, they do not encrypt. A pod that can reach the control plane and has the token can register a worker; `worker_networks` limits where the gateway dials, not who registers. Production needs TLS or a mesh; not built.
- **Secrets in Kubernetes are weaker in some ways than Compose's `env_file`**: they live in etcd (base64), are readable with `kubectl`, show up as pod environment for anyone who can `exec`, and the key-capture pod's log exists on the node until deletion. Accepted for a throwaway local cluster, written down, searched for by the verifier.
- **Control plane restarts are not zero-impact** (in-memory registry, single replica). The docs say so and PR 6 measures what clients see; fixing it (persistence or leader election) is outside this phase.
- **Gateway readiness couples to worker availability** (D13): total worker loss shows up as no endpoints rather than a JSON 503. Documented and measured; the alternative is an Open decision.
- **Kustomize load restrictor.** Referencing `observability/` files requires `--load-restrictor=LoadRestrictionsNone` and build-then-apply; anyone running `kubectl apply -k` directly gets an error. Mitigation: only the script and Makefile are documented entry points; a test pins the command.
- **Tool version skew.** `kubectl` must be within one minor of the node image; `kind` releases pin node images by Kubernetes minor. Mitigation: pinned versions, printed and compared by the preflight and the CI job; kubeconform checks against the same minor.
- **Smoke and rolling-test flakiness.** Time-based checks (scrape intervals, heartbeats, kube-proxy sync) are the usual cause. Mitigation: polls with deadlines, never sleeps; a flaky check is a bug in the check; the rolling test's denominator and its negative control keep it from passing vacuously; a single zero-failure run is evidence, so the nightly job repeats it.
- **Scope creep into Phase 18/19.** The worker pod shape, readiness semantics and `Deployment`-per-model choice anticipate them; GPU resources, HPA and model pools are not touched.
- **Kubernetes ingress ecosystem churn.** The community Ingress controller landscape is changing; no controller is chosen here, which is the point of not shipping an Ingress.

## Open decisions for the user

1. **Approve installing `kind` and `kubectl` with Homebrew** (`brew install kind kubectl`; I have installed nothing). Default: yes. Add `kubeconform` (`brew install kubeconform`) for the static job: default yes; the fallback is its container image.

Resizing `default` is rejected because it restarts everything running in it.

Default: write the policies, test enforcement in PR 5, and decide on the numbers; I recommend documenting non-enforcement over adding Calico unless it turns out cheap.

10. **CI cost:** a kind smoke job, advisory, about 10-15 runner minutes (estimate) on relevant pull requests, every master push and nightly, plus the rolling-update test nightly and on drain/gateway changes. Default: yes; the alternative is nightly only.
