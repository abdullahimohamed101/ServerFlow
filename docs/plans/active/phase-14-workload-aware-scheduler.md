# Phase 14 — Workload-Aware Scheduler: Token-Aware Strategies, an Honest Simulator, and Pre-Registered Experiments

Status: Proposed. Nothing is implemented. The "Open decisions for the user" at the end carry a recommended default each; every other decision is at the stated default D1-D28.
Owner: coding agent
Depends on: Phases 4-12 and 15 merged (master 88954f1): the registry (4), the scheduler (5), retries and attempts (6), the benchmark harness (7), the observer seam (prep, ADR-016), metrics (10), tracing (11), events (12) and fault tolerance (15: breakers, retry budget, admission queue with hand-off, drain, the chaos harness). Phase 13 (a real vLLM pool) is **not done and cannot be done without a GPU**; this plan proceeds without it and says so everywhere it matters (D1, Open decision 12).
Spec: `docs/architecture/serverflow-spec.md` §10, §12-17, §23, §32-36, §53-54, §58 Phase 14, §63, §65
Hand-offs: ADR-011 (strategies stay pure; `least-work` "remains a valid setting for Phase 14"; `least-queue` only differs where queues form early; Phase 14 owns weighted and latency-aware strategies); ADR-013 (benchmark methodology: embedded numbers compare schedulers on one machine; mock workers have no batching or contention); ADR-015 (the cost estimate `input_tokens + max_tokens` and its stated limits); ADR-012 and ADR-020 (breakers, hand-off skips the scheduler); `docs/operations/resilience.md` (a just-closed breaker's worker can wait about one heartbeat); Phase 5, 6 and 15 notes.

## Outcome

The gateway can choose a worker by **how much work is already ahead of the request and how fast that worker has recently been serving it**, not only by how many requests it holds. Three new strategies plug into the unchanged `Scheduler` interface (spec §13) and are chosen by `scheduler.strategy`:

| Name | Spec §14 | Picks |
| --- | --- | --- |
| `least-tokens` | Least Queued Tokens | the worker with the smallest estimated token work ahead of the request |
| `least-work` | Weighted Least Work | the smallest (work ahead + this request's cost) / the worker's estimated token rate: a predicted wait |
| `latency-aware` | Latency-Aware | the smallest weighted sum of predicted wait, recent time-to-first-token, GPU pressure (only where reported) and active-slot fraction |

Everything else in the phase exists so that the answer to *"is any of this better?"* can be given honestly without a GPU: a richer simulator, a deterministic offline simulator, an experiment framework in which **predictions are committed before the runs and the verdict is computed mechanically**, and a written statement of what a simulator can and cannot show.

```text
request -> handler: estimate cost once (input + output budget, same estimator as Phase 8)
        -> router.reserve (one lock): per worker, signals.Compute(...)  -> WorkerSnapshot.Observed (gateway-local)
             inputs: worker-reported metrics, this gateway's in-flight ledger (requests, estimated tokens),
                     gateway-observed TTFT per worker, decayed throughput estimate, fleet priors for cold workers
        -> scheduler.SelectWorker(ctx, req, snapshots)   // pure arithmetic over the copy, as today
        -> breaker ticket, slot, ledger entry added; released (ledger entry removed) exactly once
```

Acceptance headline (spec §58): *queued tokens, throughput, TTFT, GPU pressure and request size feed selectable strategies; hypotheses and predictions are written before the experiments; the results are compared with the predictions, including the ones that fail; all of it is documented, and every performance claim is labelled "simulator-validated, not hardware-validated".*

**What this phase will not be able to say**, stated up front because the whole design bends around it: it cannot say a strategy is better on real GPUs. The strongest sentence it can earn is of the form *"in simulator worlds W1-W4 (calibrated against N real data points from <engine>), strategy S reduced p95 latency by X% (95% interval) against B on workload shapes Z that were not used for tuning, and the ordering held in K of M perturbed worlds"*. See "GPU-free validation options".

## Non-Goals

- No machine-learning prediction, no online learning of output lengths beyond one bounded EWMA ratio if an experiment justifies it (spec §17: "Do not build ML prediction initially").
- No change to the `Scheduler` interface (spec §13, ADR-011), to the shared eligibility filter (spec §15 invariants stay in one function), or to the Phase 15 breaker, retry-budget, queue and drain semantics. Hand-off still skips the scheduler (D14).
- No change to the existing default: `scheduler.strategy` stays `round-robin` and the load overlay stays `max` until an experiment *and a user decision* say otherwise (D19, Open decisions 2-3).
- No tenant fairness, priority or token quotas in the scheduler (Phase 22); the effect of one tenant's requests on the estimates is measured and bounded (D16), not corrected.
- No cluster-wide state: each gateway keeps its own ledger and estimates, as it does its own in-flight count today. N gateways see only their own share; this is documented, not solved (Phase 8 territory), and no experiment here claims multi-gateway behaviour.
- No change to the wire protocol in v1: no new heartbeat fields, no new event fields (v1 schema), no Postgres change. Gateway-local signals only (D2, D7). Worker-reported TTFT, KV-cache usage and GPU memory *capacity* are listed as follow-ups that need real engines (Open decision 5).
- No Phase 13 work (a vLLM `Backend` for the worker agent), no autoscaling (Phase 19), no Kubernetes (Phase 17-18). A llama.cpp backend is *not* built here; Mac engine runs use the engine's own endpoints through a throw-away script (Option B).
- No use of the simulator to claim hardware results, and no default flip justified by the simulator alone.

## Current Architecture (verified in code at 88954f1)

- **Interface and strategies** (`internal/scheduler/scheduler.go`). `SelectWorker(ctx, req, workers)`; strategies do no I/O and read no clock; their only state is a seedable random source and the per-model `rotor` (round-robin position, also the tie-break). `eligible()` is the single place for spec §15: same model, `READY`, `Eligible`, `Healthy|Suspect`, `ActiveRequests < MaxConcurrency`. It returns indices ordered by worker ID; strategies copy only the chosen worker. `Strategies()` lists four names; `New` rejects anything else. `leastLoaded` is parameterised by an `int` load function.
- **`least-work` is half-built on purpose.** `config.Validate` accepts `least-work` (config.go:125), `gwtrace/vocab.go:21` allows it as a span attribute value, but a registry-mode gateway refuses to start with it ("not implemented yet"), and tests pin that (`internal/config/gateway_test.go:182`, `internal/gateway/router_test.go:478`, `tests/integration/gateway_process_test.go:125`, `internal/scheduler/scheduler_test.go:50`). Implementing it removes the refusal, so those four pins change deliberately.
- **What the scheduler sees about a worker** (`protocol.WorkerSnapshot.Metrics`): `ActiveRequests`, `QueueDepth`, `QueuedInputTokens`, `RecentTokensPerSecond`, and optional `GPUUtilization` (0-100) and `GPUMemoryUsedMB`. **There is no TTFT field and no GPU memory *capacity* field**, so memory in MB cannot be turned into a pressure fraction. The mock agent backend (`internal/worker/backend.go`, `mockStats`) reads only active, queue depth, queued input tokens, tokens/s; it never reports a GPU figure. `InferenceRequest` has `Messages`, `Prompt`, `MaxTokens` (0 = unset), `Priority`, `TenantID`; no cost field.
- **The router overlay** (`internal/gateway/router.go`, `reserve`): `ActiveRequests = max(reported, local in-flight)` (ADR-011 D6), applied to the copy before the scheduler runs; `freeSlots` (queue wake-up) uses the same rule separately. Reported load is up to one heartbeat old plus one registry refresh (embedded cluster: 1 s + 100 ms; default config: `worker.heartbeat_interval` per config, spec 2 s). The `max` is conservative upward: a stale **high** report keeps a worker out of `least-active`'s choice until the next heartbeat even though this gateway has since finished or abandoned everything it sent, which is the finding recorded in `docs/operations/resilience.md` (a just-closed breaker's worker waits about a heartbeat). A stale **low** report is hidden by the local count (the point of the overlay). Other gateways' load is invisible (Phase 8).
- **Queue hand-off** (Phase 15 PR E, `router.go` `releaseSlot`, `handoffLocked`): a freed slot goes to the head waiter of the model **without running the scheduler** (the worker's inflight count stays unchanged); breakers filter before the scheduler (`Admissible`), tickets are taken after selection and a refused ticket re-selects.
- **What the mock worker is** (`internal/mockworker`): TTFT is a constant; every generation emits tokens at its own constant `tokens-per-second`; there is **no batching, no contention, no prefill-versus-decode difference, no KV cache**; prompt length does not affect latency; `queued_input_tokens` counts words of requests **waiting in the worker's queue** only. Because the scheduler never selects a worker at `MaxConcurrency`, a worker's queue is almost always empty, so **`QueuedInputTokens` is ~0 for every schedulable worker** and `RecentTokensPerSecond` is the aggregate of the active generations (it grows with load: it measures demand, not capacity). The embedded cluster has a `heterogeneous` profile (speeds 1/0.6/0.2, TTFT factors 1/1.5/3).
- **Cost estimate** (`internal/ratelimit/estimate.go`): `EstimateRequestCost(msgs, prompt, bodyBytes, maxTokens, limit)` = ASCII bytes at three per token, non-ASCII characters whole tokens, framing, plus `max_tokens` or `gateway.max_tokens_limit` (4096) when absent. Pure (imports `utf8` and `protocol`), but lives in `internal/ratelimit`, which also owns Redis, so the scheduler cannot import it. The handler computes it only when a limiter is configured (`handlers.go:151`).
- **Benchmark harness** (`internal/bench`): seeded workloads (`workload.go`: uniform-short/long, mixed, burst, hot-model, multi-tenant; classes short 100-300/50-150, medium 500-1500/200-500, long 2000-8000/500-1500), closed and open loop, embedded cluster with `identical` and `heterogeneous` profiles, `compare` with min-max-range SPREAD (needs ≥3 repeats per side, an explicitly "not a significance test" rule), validity gate (error rate ≤5%), chaos scenarios and `Faults` (Phase 15), result schema v1 (additive). `runner` validates the scheduler name against `internal/scheduler`.
- **Observability** (ADR-016/017): an observer seam with allow-listed labels; `scheduler_decisions_total{strategy,model,result}`, `scheduler_decision_duration_seconds{strategy}`, `scheduler_selections_total{model,worker_id}` (worker label capped, 1,024-pair budget, overflow `other`), `scheduler_no_capacity_total`, `inference_ttft_seconds{model}` (from the completion event, streaming only); stated cardinality ceilings each enforced by a test; golden series files per mode.
- **Cost of a decision today**: `BenchmarkRoute` about 1 µs for 3 workers, 4 µs for 50, 54 µs for 1000 (ADR-011), against the 25 ms gateway overhead budget (spec §8).
- **Phase 13 is absent.** There is no vLLM `Backend` in `internal/worker` (`MockBackend` is the only one), and ADR-013 says "Phase 13 repeats this on real workers". No real-worker data exists in the repository.

### Findings that shape the plan

1. **The scheduler cannot currently see the work it is balancing.** Queue-based signals are empty by construction (the concurrency cap keeps workers' queues empty), and `ActiveRequests` treats a 7,000-token request like a 100-token one. The one place the true amount of work is known exactly is **this gateway's own request set**: it knows what it sent, to whom, and an estimate of each request's size. So the primary signal for the new strategies is a gateway-side **ledger of estimated tokens in flight per worker** (D4), and the worker-reported figures are secondary and corrected for staleness against it.
2. **Observed throughput conflates demand with capacity.** A worker with little to do reports a low tokens/s. Using it directly as a divisor makes idle workers look slow (and an empty one infinitely slow). The capacity estimate must be a decayed *peak* or a per-slot rate, with a cold-start prior (D6).
3. **A learned signal that can only be refreshed by picking the worker can exile it.** A TTFT estimate that rose during an incident, on a worker the strategy then stops choosing, never falls. Every learned estimate decays toward the fleet prior with time (D7), and a test pins "recovered worker is picked again within a bound".
4. **Unit mismatches are real here.** The mock worker counts words as tokens; the gateway estimates three bytes per token; prefill and decode tokens cost different time on a real engine; `RecentTokensPerSecond` counts output tokens only. The design uses the gateway's single estimator for all gateway-side work, uses reported token counts only as a bounded additive term, and exposes the input/output weight as a configuration value (D3, D5).
5. **The simulator the repository has is the wrong shape for the question.** On the current mock worker, any token-aware strategy is predicted to be indistinguishable from `least-active` on identical workers (H2): the experiment can show only that. Without batching, prefill cost and KV pressure, "workload-aware" has nothing to be aware of. Hence the simulator work (D21-D23).

## Decisions (confirm before implementation)

### Strategy semantics

- **D1 Scope, names, registry-only.** Three strategies, names `least-tokens`, `least-work`, `latency-aware`, added to `scheduler.Strategies()`, `config.Validate`, `gwtrace/vocab.go` (`least-tokens`, `latency-aware`; `least-work` exists) and the runner's name check. They take effect only in registry mode (the scheduler is not used in static mode); configuring one with `worker_source: static` is accepted and ignored, like every registry-only setting. The "not implemented yet" refusal for `least-work` is removed in the PR that implements it, and its four pinning tests are rewritten to pin the new truth, not deleted. Phase 13's absence is recorded in ADR-022 as a deviation from spec order.
- **D2 Signals travel on the snapshot copy, strategies stay pure.** `protocol.WorkerSnapshot` gains one field `Observed ObservedLoad` tagged `json:"-"`: it is never serialised or deserialised, so the wire format is byte-identical (golden test), and a hostile or buggy control plane cannot inject a value into it. `ObservedLoad` is a plain struct of gateway-computed numbers (D5): `InflightRequests`, `WorkAheadTokens`, `CapacityTPS`, `TTFTSeconds`, `EffectiveActive`, `Flags` (cold start, stale, missing GPU, invalid; bit set). The router fills it on its private copy inside the existing critical section; strategies do arithmetic on it and read no clock. Rejected: context values (hidden magic, untestable by signature); a second `Scheduler` method or interface (the spec says every strategy implements the one interface); overloading `Metrics.QueuedInputTokens` (changes the meaning of a field the registry also serves and dashboards display); changing `SelectWorker`'s signature (ADR-011 rejected it); strategies owning state and a clock (breaks "no clock, no I/O" and deterministic tests).
- **D3 Request cost estimation (spec §17).** Computed **once per request in the handler** (also when no limiter is configured), from the same estimator Phase 8 uses, extracted unchanged into a new pure package `internal/cost` with `ratelimit` delegating to it (a test pins identical outputs over a corpus and a randomised comparison, so billing does not move). Two numbers on `InferenceRequest`: `EstInputTokens` and `EstOutputTokens`. Output estimate = `ceil(output_fraction * (max_tokens or gateway.max_tokens_limit))`, `output_fraction` default **1.0** (the pessimistic "start simple" estimate of spec §17 and Phase 8). Work cost of a request = `input_weight * EstInputTokens + EstOutputTokens`, `input_weight` default **1.0** (spec §17 "input + max_tokens"). Both knobs exist because the plan *predicts the defaults are wrong in specific regimes* (H5, H6) and the experiments must be able to show it; neither is tuned except on the tuning split (D26). Sources considered:

  | Source | Verdict |
  | --- | --- |
  | Client-supplied `max_tokens` (with the gateway limit when absent) | **Default.** Available before routing, already validated and capped (`max_tokens_limit`), same basis as quota. An upper bound on output, so work is overestimated for requests that stop early. A client can inflate its own estimate (bounded by the cap); it can only make workers look busier to later requests, which is a small cross-tenant effect, measured in the multi-tenant run and documented (D16). |
  | Prompt length from the request body | **Default for input.** Bytes-per-token approximation; low for dense text (stated in ADR-015). |
  | Worker-reported `QueuedInputTokens` | Used only as a bounded additive term (D5): it counts the worker's own units (mock: words) and only waiting requests. |
  | Observed actual output length (parse `usage`/count SSE chunks) | **Rejected for v1**: the gateway relays bodies without parsing them (ADR-003); parsing adds a hot-path cost and a new failure surface. If H6 shows the output estimate dominates error, a bounded per-model EWMA of `actual/max_tokens` from non-streaming `usage` only is the named follow-up (Open decision 6). |
  | Per-tenant or per-prompt-type history | Rejected (spec §17 "do not build ML"; Phase 22). |

- **D4 In-flight ledger (the primary signal) and overlay model v2.**
  - *Token ledger.* `internal/scheduler/signals` (new, pure, clock passed in, no goroutines) keeps per worker (keyed like breakers by worker ID and `RegisteredAt`): the count and the summed work cost of this gateway's in-flight requests. `Add` happens in `reserve` next to `inflight[id]++`, `Remove` next to the existing `release`, **exactly once** (the `sync.Once` already there), including on panic paths and on the hand-off path: a hand-off keeps the worker's slot but the *request* changes, so the ledger must subtract the finished request's cost and add the waiter's (the likeliest bug site; a dedicated test and mutants, D14). Work in flight is not credited for progress in v1 (no body parsing); a request counts its full cost until it ends. Stated bias: long-running requests look heavier than their remaining work.
  - *Overlay model v2 for `ActiveRequests` (opt-in).* Replace `max(reported, local)` with a heartbeat-aligned correction: `effective = max(local, reported + started_since_hb - finished_since_hb)`, where the ledger keeps a bounded, coarse (100 ms buckets, window = `registry_max_staleness` + one heartbeat interval) history of this gateway's starts and finishes per worker, and `since_hb` is measured from the **gateway-local time the report was made**, `snapshot.fetched - HeartbeatAgeSeconds` (the same clock-domain-free arithmetic the snapshot cache already uses to age workers). Intuition: requests this gateway started *before* the report are inside `reported`; those it finished *after* the report are still counted there and must be subtracted; those it started after the report are not yet in it and must be added. The `max` rule gets the first and third cases wrong in the stale-high direction: it is the "recovered worker sits unpicked" finding. The floor `local` keeps the guarantee the overlay exists for. Worst case when history is missing (new gateway, evicted bucket) falls back to today's `max(reported, local)`; it never produces a lower-than-local value.
  - *Switch.* `scheduler.load_overlay: max | ledger`, **default `max`** (byte-identical behaviour; differential test). `ledger` changes `ActiveRequests` for **all** strategies and for the `AtCapacity` check and `freeSlots`, so both call one shared function. It is decided by experiment E0 whether it is worth recommending (Open decision 3).
  - *Bounds.* Entries pruned when a worker leaves the snapshot or re-registers (as `Prune` for breakers); a cap on tracked workers (4,096; beyond it, untracked workers use cold-start behaviour, counted); history buckets bounded; a worker-ID churn test shows no growth.
- **D5 Work-ahead and predicted wait (exact formulas, so tests and the ADR can pin them).** For request `r` with work cost `c_r` and worker `w` (all terms computed by the router with `signals.Compute`, in tokens unless stated):
  - `L_w` = ledger work in flight (D4).
  - `F_w` = `foreign_w * mean_cost_m`: `foreign_w = max(0, effective_active_w - local_inflight_w)` is the load other gateways and clients appear to add; `mean_cost_m` is a per-model EWMA of the work cost of requests this gateway routed (bounded, cold value = `c_r`). Zero in a single-gateway deployment up to staleness residue.
  - `Q_w` = reported `QueuedInputTokens`, clamped to `[0, 2^31)`, times `input_weight`. It can double count requests this gateway also holds in its ledger, **only on workers that are queueing**, which is the direction wanted (avoid a queueing worker); it is not de-duplicated, and the ADR says so.
  - `WorkAhead_w = L_w + F_w + Q_w`.
  - `R_w` = capacity estimate in tokens/s (D6); 0 = unknown.
  - `least-tokens`: minimise `WorkAhead_w`. Ties take turns (rotor).
  - `least-work`: minimise `predicted_wait_w = (WorkAhead_w + c_r) / R_w` (spec §14 item 6: work divided by recent throughput; the request's own cost is included so heterogeneous speeds differentiate). Unknown `R_w` uses the fleet prior (D6); when no worker has a rate, the strategy degenerates to `least-tokens` and counts a `cold_start` fallback.
  - `latency-aware` (spec §14 item 7): `score_w = w_wait * predicted_wait_w + w_ttft * ttft_w + w_gpu * gpu_pressure_w + w_active * active_fraction_w`, in **seconds-equivalent** units so the weights are interpretable (alpha, beta, gamma, delta of the spec map to `w_wait`, `w_ttft`, `w_gpu`, `w_active`): `ttft_w` seconds (D7); `gpu_pressure_w` = reported `GPUUtilization/100` or 0 when absent (D8); `active_fraction_w` = `effective_active_w / MaxConcurrency`. Defaults chosen from mechanism **before** any comparison run: `w_wait=1, w_ttft=1, w_gpu=0, w_active=0` (so the default is "wait plus TTFT", the two terms with a unit and a mechanism; GPU and active fraction are opt-in tie-shaping). Tuning is allowed only on the tuning split (D26).
  - Ties and floating point: a score within `1e-9` relative of the minimum is a tie; ties take turns by worker-ID order through the rotor, so the result is deterministic and starvation-free for equal scores. NaN, infinite or negative inputs are sanitised to the neutral value before scoring (never a panic, never a choice of an ineligible worker, because `eligible()` already ran).
- **D6 Throughput as capacity, and cold start.** `R_w` is a **decayed peak of reported `RecentTokensPerSecond` sampled only while `ActiveRequests >= 1` and the report is fresh** (peak window 60 s with a 30 s half-life decay, `scheduler.signals.capacity_halflife`), not the latest value, so an idle or lightly-loaded worker is not mistaken for a slow one (finding 2). Alternatives considered: the latest value (rejected: demand, not capacity); per-slot rate `tps/active * MaxConcurrency` (right for the current mock, wrong for a batching engine whose aggregate saturates; kept as the *simulator-only* diagnostic to compare against, H-calibration); a configured per-worker tokens/s (rejected: static, wrong when workers differ silently). A worker with no sample, or a freshly (re)registered one, uses the **median `R` of the model's sampled workers** (the fleet prior); if none, `R` is unknown for all and the strategies fall back as in D5. The fallback never gives a cold worker an optimistic zero cost (that floods it) or an infinite one (that exiles it). Each fallback increments `scheduler_signal_fallbacks_total` (D24). Reported throughput is output tokens only while work cost counts input too; `input_weight` (D3) is the only knob that reconciles them, and H5 predicts the default is wrong for prefill-heavy loads.
- **D7 TTFT is gateway-observed, not worker-reported.** The gateway measures, per attempt, time from the request being sent to the first body byte (the instant the Phase 15 ok-verdict is given at the first byte), for attempts that end ok. It feeds a per-worker EWMA (`scheduler.signals.ewma_alpha`, default 0.2) with time decay toward the fleet median with half-life `scheduler.signals.ttft_halflife` (default 10 s) so a stale estimate cannot exile a worker (finding 3), a sample clamp (`[1 ms, 60 s]`), and a minimum of `min_samples` (3) before the estimate is used (below it, the fleet prior). Failed, neutral, cancelled and probe attempts record nothing here (the breaker owns fault handling; a probe's latency is not representative). It is recorded by a direct call from the attempt code to the signals package, **not** through the observer seam: observers are for telemetry and are panic-guarded and reorderable (ADR-016); a control-flow input must not depend on them. TTFT measured at the gateway includes any worker-side queue wait and network time, which is what the client experiences and what the strategy should avoid. No wire change.
- **D8 GPU pressure is optional and weak.** Used only when `GPUUtilization` is non-nil and the report is fresh: `pressure = util/100`. `GPUMemoryUsedMB` is **not** used: without a reported total memory it cannot be a fraction, and inferring one from history would be a guess presented as a signal (a protocol addition is the follow-up, Open decision 5). Missing figure: the term contributes 0 and the fallback counter increments; it never penalises a worker for being unable to report. Utilisation is a saturating indicator (a GPU at 100% can still accept batched work), so `w_gpu` defaults to 0 and H8 predicts it adds nothing. The mock agent backend gains optional `gpu_utilization`/`gpu_memory_used_mb` parsing from the simulator's `/stats` so the path is testable (PR E); real GPUs are Phase 13/18.
- **D9 Invariants and metamorphic properties.** Spec §15 holds unchanged because all strategies start from `eligible()`. Added properties, tested for every strategy over random views (including breaker-filtered and overlay-modified ones): (I1) the chosen worker is always eligible; (I2) determinism: same inputs and a fresh rotor give the same choice; (I3) monotonicity: raising one worker's `WorkAhead` (all else equal) never makes it more likely to be chosen; (I4) with all workers' signals equal, the choice is the rotor's tie order; (I5) any worker with garbage signals scores neutrally and the call neither panics nor blocks; (I6) bounded exile: with a fake clock, a worker whose estimates are worst is chosen again within `ttft_halflife * k` once its signals decay; (I7) `SelectWorker` allocates no more than one worker copy.

### Interaction with the rest of the system

- **D10 Staleness handling summary.** Local facts (ledger) are exact; reported figures are as old as one heartbeat plus one refresh; the snapshot cache already ages heartbeat time. Rules: reported `ActiveRequests`, `QueuedInputTokens`, `RecentTokensPerSecond` and GPU are used only while the worker is `Eligible` (so within the suspect threshold); `ledger` overlay corrects active counts (D4); queue and tokens/s are not corrected (no local counterpart) and their use is bounded (D5, D6); a snapshot older than `registry_max_staleness` is not used at all, as today. Measured, not asserted: E0 (D25) quantifies the improvement of `ledger` over `max`, and the experiment doc reports the residual.
- **D11 Breakers.** Unchanged order: breakers mark workers ineligible in the copy before signals and the scheduler run; ticket acquisition after selection still re-selects on refusal; a half-open worker is admissible only per Phase 15 rules. New requirement from finding 3: a half-open worker that the strategy ranks poorly must still be probed. Probing is driven by `Acquire` after selection, so a poorly ranked half-open worker could go unpicked: the fleet-prior decay (D6, D7) bounds this, and test (I6) plus a chaos-style test ("recover after a fault, picked again within X s under `latency-aware`") pin it. If the test fails, the fix is in this plan's scope (a probe-priority rule in the router, not in the strategy), and the PR says so.
- **D12 Cold start and unknown workers.** A new or re-registered worker (`RegisteredAt` changes) starts with an empty ledger (correct: nothing in flight), no TTFT samples and no capacity sample; D6/D7 priors apply; its share in its first seconds is a pre-registered measure (H9). A worker the registry has not yet shown to be `READY` is not eligible, as today.
- **D13 Errors and shedding.** `NoWorkerError` semantics unchanged. A strategy never returns "no worker" when `eligible()` returned some. Shedding and queue reasons are untouched.
- **D14 Phase 15 hand-off skips the scheduler.** v1 keeps it (work-conserving, FIFO, fair to waiters), and measures the cost: under overload the queued request inherits whichever worker freed first, which can be the slow one, so **strategy differences are predicted to shrink under queueing (H10)**. The ledger is updated on hand-off (subtract old, add new) with the router lock held; a hand-off declined or re-routed leaves the ledger consistent. A quality-aware hand-off (offer the slot to the head only if the freeing worker's predicted wait is within a margin of the best) is named, not built (Open decision 13), because it trades FIFO fairness and work conservation, both Phase 15 properties.
- **D15 Retries.** A retry excludes tried workers and re-runs the strategy, so its cost is added on the new worker and removed from the failed one at attempt end. The retry budget and deadline are untouched.
- **D16 Tenants and fairness.** The scheduler remains tenant-blind. The multi-tenant workload (one aggressive tenant, ten times the traffic) is run **descriptively**: per-tenant p95 under each strategy, to expose any case where a heavy tenant's inflated `max_tokens` distorts other tenants' latency. Bounds already in place: `max_tokens_limit` caps the estimate; `output_fraction` scales it. No claim of fairness is made; Phase 22 owns it.
- **D17 Panic and leak safety.** `Add`/`Remove` are paired with the router's slot release (`once`), including `reserve` returning an error after partial work, a panic in a strategy (the existing deferred unlock stays), ticket-refusal re-selection, and hand-off. A test injects a panicking strategy and asserts the ledger returns to zero. Memory bounded as in D4.
- **D18 Per-decision cost and lock.** `signals.Compute` runs inside the existing `r.mu` section; budget (benchmarked, `BenchmarkRoute` extended): ≤ 25 µs at 50 workers, ≤ 400 µs at 1,000 for any new strategy; the gateway overhead test (25 ms p95) and the observer benchmark (0 allocs/op for the request-path metrics methods) must not regress. If the budget is exceeded the computation moves to refresh time for the slow-moving terms (capacity, TTFT decay) and only the ledger terms stay per request.

### Simulation and experiments

- **D21 Two simulators, one source of truth for signals.** (1) **Richer mock worker** (`internal/mockworker`, new `--model-engine sim` mode; default behaviour unchanged): continuous-batching decode with step time `t0 + t1*b` for batch `b` (per-request rate falls as the batch grows; aggregate saturates), prefill time proportional to input tokens at a separate rate (and blocking decode steps for the batch while it runs, optionally chunked), a **KV-cache token budget** (running requests reserve `input + generated`; when full, new requests wait in the worker's queue, so `queue_depth` and `queued_input_tokens` become non-zero *before* `max_concurrency` is reached, the regime ADR-011 says `least-queue` was made for), seeded lognormal noise on step time and TTFT, true output lengths drawn independently of `max_tokens` (a fraction with a seeded distribution; so H6 is testable), heterogeneous profiles (fast/slow generations: different `t0`, `t1`, KV size, concurrency), and honest `/stats` fields including simulated `gpu_utilization` (batch fill) and `gpu_memory_used_mb` (KV bytes + weights). Real-time, so it exercises the real gateway, registry, heartbeats and staleness end to end. (2) **Offline discrete-event simulator** (`internal/bench/sim`, virtual clock): the same worker model and the same workload generator, plus an explicit model of heartbeats and snapshot refresh delay and of the gateway's ledger (it imports `internal/scheduler` and `internal/scheduler/signals`, so it drives the **same code** that ships). Deterministic, fast (minutes for hundreds of cells), no wall-clock noise, so it carries the experiment matrix and the sensitivity sweeps; the real-time path confirms a few headline cells and the staleness behaviour. Rejected: only the real-time mock (a thousand-cell matrix is impractical and every cell carries laptop scheduling noise; ADR-013 already found CPU starvation effects); only the DES (it would not exercise the gateway's real overlay, locks, hand-off and heartbeat timing, which are the things most likely to break the strategies in practice).
- **D22 Calibration story.** Simulator parameters are not "chosen to make strategies look right". They are (a) set from published/observed shapes and (b) **fitted to measured data** where any exists, recorded in a versioned parameter file with provenance and a fit-quality statement: Option B data from a Mac llama.cpp server (prefill ms/token vs length, decode step time vs batch, KV-slot saturation behaviour, noise coefficient of variation) and, if the user approves, Option C data from a rented GPU. The calibration reports what the simulator reproduces and what it does not (e.g. the shape of `step_time(b)` yes; absolute numbers no). Parameter files are frozen and hashed at the predictions freeze (D26); the hash is in every result.
- **D23 Worlds (frozen sets).** W0 current mock, identical; W0h current mock, `heterogeneous` profile; W1 sim, batching, homogeneous; W2 sim, heterogeneous generations; W3 sim, KV pressure (queues form before the concurrency cap); W4 sim, noisy (CV of step time 0.3) with heterogeneity; plus perturbation variants of W1-W4 at ±30% on `t0`, `t1`, KV size, prefill rate and noise (for H13). **Tuning set** (the only worlds/workloads/seeds on which any weight may be adjusted): W1, W2 with workloads `mixed` and `heavy-tail`, seeds 1-10. **Held-out set** (never used to adjust anything): W3, W4, all perturbation variants, workloads `prefill-heavy`, `decode-heavy`, `burst`, `multi-tenant`, a workload authored blind by the independent verifier, seeds 101-120. Negative controls (all strategies predicted equal): W0 with `uniform-short` at 50% load and W1 homogeneous `uniform-short` at 50%.
- **D24 Observability (observer seam, bounded labels).** Added only when a new strategy or `ledger` is configured: `scheduler_predicted_wait_seconds{model}` (histogram of the chosen worker's predicted wait at decision time), `scheduler_prediction_error_seconds{model}` (histogram: actual time to first byte minus predicted wait plus TTFT estimate, observed at the first byte; the calibration instrument, so a strategy whose predictions are wrong is visible in production, not only in a report), `scheduler_signal_fallbacks_total{model,reason}` (`cold_start`, `stale`, `missing_gpu`, `invalid`, `untracked`), read-at-scrape `worker_estimated_inflight_tokens{worker_id,model}` (worker label under the existing cap and the `other` folding precedent of `circuit_breaker_state`). **No new label name**, no per-request or per-tenant labels. The observer seam gains `AttemptStart.Predicted` (a small struct: `EstCost`, `PredictedWait`, `Strategy flags`) so metrics and tracing read one source; tracing span attributes `serverflow.est_tokens`, `serverflow.predicted_wait_ms` added to the allow-list; the event schema (v1) is **not** changed; logs gain the estimate and prediction at debug level only. Ceilings added to ADR-017 and enforced by the all-registries label test and a 1,000 workers x 1,000 models series bound. Grafana: Scheduler dashboard gains prediction error and fallbacks panels (verified by the dashboard tests and promtool as for earlier phases). Observer hot path stays at 0 allocs/op.
- **D25 Experiments are hypotheses with written predictions, committed first.** Protocol: (1) the hypotheses file `docs/benchmarks/phase-14-predictions.md` states, for each of H1-H13 (drafts below): the claim, the mechanism that predicts it, the world, workload, load level, seeds, metric, direction, **numeric threshold for "confirmed"**, threshold for "refuted", the confidence the author holds, and what would make the run invalid; (2) the file is **committed and merged in its own docs-only PR (I) before any strategy-comparison run exists**; the PR text and the results document cite the commit; the independent verifier checks `git log` ordering and that no result file predates it; (3) a mechanical **verdict tool** (`benchmark verdict --predictions <file> --runs <dir>`) evaluates each prediction from machine-readable result files (the predictions file carries a fenced, parseable block per hypothesis), prints confirmed / refuted / inconclusive, and the results document includes its output **verbatim**, with a human commentary section that may explain a failure but may not change a verdict; (4) a prediction that fails is reported as failed in the same table, with what it taught; (5) changes to the predictions after the freeze are made only as dated amendments listed at the end of the file and never apply to the run they would have rescued; (6) comparison metrics are the pre-registered primaries only (p95 end-to-end latency, p95 TTFT, at 80% of capacity, per world and workload), guarded by error/shed rate not rising, decision cost within D18, and invalid-run handling per ADR-013; everything else is descriptive and labelled so. This follows spec §65 (build, measure, hypothesise, change, benchmark, compare, document).
- **D26 Statistics, tuning discipline and guards against tuning to your own simulator.**
  - DES: 20 seeds per cell, **paired by seed** (same workload for every strategy), reported as the median paired difference with a bootstrap 95% interval (fixed resampling seed), a claim only if the interval excludes zero *and* the median reaches the pre-registered threshold. Real-time embedded cells: 5 repeats per side, the ADR-013 min-max SPREAD rule (retained and reported), plus the same bootstrap interval when pairing is possible. Multiple comparisons are limited to the pre-registered primaries (≤ 8 hypotheses carry a primary claim); the rest is descriptive.
  - Tuning: only on the tuning set; at most one tuning pass with a written objective; the tuned values are recorded and frozen **before** held-out runs; the held-out result is what is reported; tuning on held-out data invalidates the experiment (the verdict tool refuses a tuned-values file whose timestamp/hash is newer than the freeze).
  - Guards: held-out worlds/workloads/seeds (D23); negative controls (must show no difference; if a signal strategy "wins" a control the harness is suspect and the run set is invalid); a placebo (the same strategy under two seeds) to measure the noise floor; a **rank-stability** report (the ordering of strategies in each perturbed world, headline = fraction of worlds in which the ordering holds, H13), not just the best-case gain; the simulator's own parameters fixed at freeze and hashed; the independent verifier designs one workload and one world variant blind and runs them; and every result table is headed *"simulator-validated, not hardware-validated"*.
  - Default-change criteria (used only by PR L): confirmed on held-out in ≥ 80% of perturbed worlds, no control regression, no error-rate or latency-tail regression against the baseline anywhere in the matrix, decision cost within budget, calibration against at least one real engine, **and** for a default flip of the *strategy*: hardware evidence (Option C) or an explicit user acceptance recorded in the ADR. Without all of these the default stays.
- **D27 Deliverables of the evidence.** `docs/benchmarks/phase-14-simulator.md` (model, parameter files, calibration, what it reproduces and does not), `docs/benchmarks/phase-14-predictions.md` (frozen predictions), `docs/benchmarks/phase-14-results.md` (verdict output verbatim, tables with ranges/intervals, invalid runs and why, failed predictions with analysis, controls, rank stability, negative results, "cannot show" section), `docs/benchmarks/phase-14-sample/` (a small committed subset of result files, as Phase 7 did), `benchmark compare` unchanged for humans. Results never state a strategy is "better" without the scope sentence of the Outcome.
- **D28 Order of operations that protects honesty.** (1) Strategies, signals and simulators are built and unit-tested, and **no scheduler-comparison run is made** (smoke runs prove the pipeline works and are discarded, listed as such). (2) Calibration (Mac) may run at any time before the freeze because it measures an engine, not a scheduler. (3) Freeze: predictions + parameter hash + tuning split. (4) Tuning pass on the tuning set, tuned values frozen. (5) Held-out and control runs. (6) Verdicts, then the write-up. Reordering any step is recorded in the results document as a deviation.

## Proposed Design

**Request flow with a workload-aware strategy** (registry mode, strategy configured): handler estimates cost once -> limiter and admission as today -> `route`: view -> breaker filter -> `reserve` (one lock): `signals.Compute` per candidate (ledger, overlay, priors, decay) -> `SelectWorker` (pure) -> breaker ticket -> ledger add + slot -> send -> first byte: TTFT recorded, prediction error observed -> end: ledger removed, slot released (hand-off: ledger moves to the waiter).

## Acceptance Criteria

Bracketed letters name the PR that must satisfy the criterion (PR breakdown below).

1. **[A] Off means off.** With default configuration and with `scheduler.strategy` set to any existing strategy and `load_overlay: max`: a differential test against recorded master outputs (status, body, headers minus IDs/dates, normalised logs, `/metrics` series names) is identical; golden series files are unchanged; the `protocol.WorkerSnapshot` JSON is byte-identical (the `Observed` field never serialises; a control-plane response carrying `"Observed"` or `"observed"` is ignored).
2. **[A] Estimator extraction.** `cost` produces outputs identical to the old `ratelimit` functions over a corpus and 100,000 randomised requests (billing does not move); the handler sets `EstInputTokens/EstOutputTokens` with and without a limiter; estimation cost ≤ 50 µs for a 100 KB body; the gateway overhead test (25 ms p95) does not regress.
3. **[B] Ledger correctness.** With a fake clock: add/remove pairs return the ledger to zero on success, error, panic in a strategy, ticket-refusal re-selection, client cancel, retry, and hand-off (old cost removed, waiter's cost added under `router.mu`); a double release is harmless; re-registration and worker removal reset and prune; worker-ID churn (100,000 IDs) does not grow memory beyond the cap; tracked-worker cap falls back to cold start and counts it.
4. **[B] Overlay v2.** Table-driven over the cases of D4 (started before/after the report, finished before/after the report, missing history): `ledger` never returns below `local`; equals `max` when history is missing; a stale-high report no longer hides a worker the gateway has emptied; a stale-low report is still covered by `local`; `AtCapacity` and `freeSlots` use the same function (a test fails if they diverge); a randomised model check against a naive reference implementation; default `max` unchanged (criterion 1).
5. **[B][E0] Recovered worker (staleness finding).** In the embedded cluster with `least-active`, a worker whose stuck requests are abandoned and whose breaker closes is first picked again within the bound pre-registered as H1 under `ledger`, and the same test on `max` documents today's wait. Reported, not gated on the numbers, gated on the test existing and being deterministic.
6. **[C] Strategy invariants and properties.** For `least-tokens`, `least-work`, `latency-aware`, over random views including breaker-modified and overlay-modified ones: I1-I7 of D9 as property/metamorphic tests; `scheduler_ineligible_selections_total` stays 0; tie order equals the rotor's; NaN/Inf/negative/huge inputs never panic, block or select an ineligible worker; allocation bound I7.
7. **[C] Formulas pinned.** Hand-computed examples for each strategy (tokens, wait, score) with exact expected choices; the degenerate cases (no `R` anywhere: `least-work` equals `least-tokens` plus a `cold_start` fallback; no GPU data; single candidate); `w_gpu = w_active = 0` makes `latency-aware` independent of GPU and active count (mutation-sensitive).
8. **[C] Cold start and exile.** A freshly registered worker uses fleet priors, never zero-cost or infinite-cost; (I6) a worker with worst estimates is picked again within `k * ttft_halflife` of fake time; a half-open breaker worker under `latency-aware` is probed and closed within a pre-registered time (D11); if this fails the router gets the probe-priority fix inside the same PR.
9. **[C] Configuration.** Defaults, YAML, env overlay, every bound, cross-checks (weights not all zero, `output_fraction` in (0,1], half-lives ≥ 1 s); `least-work` accepted and implemented in registry mode (the four pinned tests rewritten, not removed); unknown names still rejected with the supported list; static mode ignores the keys; invalid values ignored from env with a startup log line, as other numeric overrides.
10. **[C] TTFT signal.** Recorded only for attempts that end ok at the first byte; not for probe, neutral, failed or cancelled attempts; clamped; time-decayed to the fleet median; `min_samples` honoured; recorded by a direct call (a panicking or removed observer does not change scheduling: a test removes all observers and gets identical choices).
11. **[C] Decision cost (H12).** `BenchmarkRoute` extended with each new strategy: ≤ 25 µs at 50 workers and ≤ 400 µs at 1,000 (parallel, as ADR-011 measured); `-race` clean; no new allocations beyond the budgeted ones; overhead test unchanged.
12. **[D] Observability (D24).** New series exist only when configured; all-registries label test passes with **no new label names**; the 1,000 x 1,000 ceiling test passes with the new families; `worker_estimated_inflight_tokens` folds workers beyond the label cap into `other`; histogram buckets documented; hot-path observer methods 0 allocs/op; span allow-list test passes with the new keys; log, event and metric output contains no prompt, key or body text (hostile-input test); prediction error is recorded at the first byte and for no other moment; golden additions reviewed; promtool and dashboard tests pass; the event schema v1 is unchanged.
13. **[E] Simulator behaviour (each property a deterministic unit test on the engine with a fake clock).** Per-request token rate falls as batch grows and aggregate rate saturates; prefill time scales with input length; KV budget exhaustion queues the next request and `queue_depth`/`queued_input_tokens` become non-zero before `max_concurrency`; true output length distribution follows its seed and is independent of `max_tokens`; the same seed reproduces the same trace; noise has the configured coefficient of variation within tolerance; `/stats` reports GPU fields only in sim mode; default mock behaviour is unchanged (existing tests untouched and green); parameter files validate and are hashed.
14. **[F] Offline simulator.** Deterministic (same seed, same bytes); matches the real-time sim engine's unit-level behaviour on shared test vectors (same engine code or an equivalence test); drives the shipped `scheduler` and `signals` packages (an import test); models heartbeat interval, refresh delay and the ledger; 20 seeds x one cell runs in seconds; a cell with an injected known-optimal oracle strategy (omniscient least-remaining-work) bounds what any strategy can gain.
15. **[G] Workloads and runner.** `heavy-tail`, `prefill-heavy`, `decode-heavy` have pinned digests; existing workload digests unchanged; runner accepts the new strategies and sim worlds, records world, parameter hash, strategy options and overlay in `result.json` (additive; schema v1); `compare` warns when two groups differ in any of them; the validity gate applies to sim runs.
16. **[G] Verdict tool.** Given a predictions file and result files it prints a verdict per hypothesis; a table-driven test covers confirmed, refuted, inconclusive (interval includes zero), invalid input, a missing group, a tuned-values file newer than the freeze, and a predictions file edited after the freeze (hash mismatch is reported); it never edits a prediction.
17. **[H] Calibration.** `docs/benchmarks/phase-14-simulator.md` contains measured prefill, decode-versus-batch, KV-slot and noise data from a named engine, model, quantisation and machine, the fitted parameters, the fit quality, and an explicit list of what the simulator does not reproduce; scripts are reproducible and contain no secrets or model downloads committed.
18. **[I] Freeze.** `phase-14-predictions.md` is merged alone (docs only), contains all hypotheses with numeric thresholds, the world/workload/seed lists for tuning and held-out, the parameter-file hashes, the tuning objective and the statistics rules; the verifier confirms by `git log` that no result file or comparison run output predates it.
19. **[J] Results.** Verdict output verbatim; every hypothesis reported including the refuted; tuning only on the tuning set with frozen values published before held-out runs; controls and placebo shown; rank stability reported; invalid runs and reasons listed; no claim from an interval that includes zero; every table headed "simulator-validated, not hardware-validated"; a "cannot show" section; deviations from D28 listed; a result that contradicts a prediction is analysed, not explained away.
20. **[J] Honest default.** The default strategy and overlay in the shipped configuration are as D19 states unless PR L was approved; documentation tells operators that the new strategies are opt-in and what is unproven.
21. **[all] Quality gate.** `gofmt`, `go vet`, `go build`, `go test -race ./...`, `golangci-lint`, `scripts/quality.sh full`, CI steps run locally per PR; timing-dependent tests `-race -count=10`; nothing reads the wall clock inside strategies or the signals package (an import/grep test).
22. **[all] Compatibility.** A gateway on this branch with defaults interoperates with the master control plane and workers unchanged (process test with master binaries is not required; the wire is byte-identical by criterion 1).

- **Benchmarks:** `BenchmarkRoute` per strategy; estimator; observer allocations; Phase 2 overhead test.
- **Experiment verification:** the verdict tool is the only producer of verdicts; the verifier re-runs a sample of cells from the committed parameter files and compares bytes (DES) or ranges (real-time).
- **Independent verifier brief** (`verify-change`, fresh context, per PR and again on J): (a) differential master-vs-branch with defaults and with existing strategies and `max` overlay, requests/headers/logs/series; (b) hostile inputs: `max_tokens` extremes and absent, 1 MiB bodies, non-ASCII floods, many models and workers, worker-ID churn, a control plane that returns NaN/negative/huge load and a forged `observed` key, workers that report absurd `queued_input_tokens` or tokens/s, a worker that never reports a GPU, clients cancelling mid-queue, retries during a hand-off; (c) leaks after chaos-style runs (ledger, history, tickets, waiters, goroutines); (d) mutation testing — ledger: add without remove, remove twice, remove on the wrong worker, hand-off not moving cost, cost not removed on panic, not reset on re-registration, never pruned; overlay: `max` instead of ledger, floor removed, started/finished sign swapped, history window off by one, report time taken as fetch time, `AtCapacity` using a different function; estimator: output fraction ignored, input weight ignored, input/output swapped, absent `max_tokens` treated as 0; signals: capacity from the latest rather than the peak, peak never decaying, idle samples included, cold worker given zero cost, cold worker given infinite cost, TTFT not decaying, failed attempts recorded, probe attempts recorded, clamp removed, `min_samples` ignored; strategies: `>` for `<`, wait without the request's own cost, wait ignoring `R`, work ignoring `Q`, GPU term applied when absent, weights swapped, tie epsilon removed, rotor bypassed for ties, ineligible workers scored; observability: label added, prediction error at the wrong moment, fallback not counted, series present when off; verdict tool: threshold comparison flipped, tuned-after-freeze accepted, interval ignored, missing group treated as pass. Every surviving mutant is killed by a new test or argued equivalent; (e) experiment audit: the predictions commit precedes every result file; thresholds in the verdict equal those in the file; tuning data disjoint from held-out; the blind workload exists; controls were run; invalid runs are listed, not dropped.
- **Review:** `review-change` then `harden-change`; the ledger and hand-off changes touch the router's concurrency core and get an explicit race-and-leak look; the `Observed` field and the external-JSON path get a security look (a control plane must not be able to set scheduling signals).

## GPU-free validation options

The question is not "simulator or GPU" but *which claims each source of evidence can carry*. A scheduler's quality depends on (i) the **shape** of per-request cost (prefill vs decode, batch scaling, KV pressure, variance), (ii) the **workload** (length mix, burstiness, tenants), and (iii) the **control loop** (staleness, estimation error, interactions with breakers and queues). A simulator is good at (iii) and at exploring (ii) given (i); it is only as good as the calibration of (i) and cannot discover shapes nobody put into it.

### (a) A richer simulator (D21-D23): batching, KV pressure, prefill/decode, heterogeneity, noise

- **Answers:** whether the *logic* is right (invariants, determinism, starvation, cold start, staleness handling, ledger correctness); whether signals, estimators and priors behave in the control loop with realistic delays; **which workload and world properties a token-aware strategy depends on** (e.g. does it matter only when lengths are heavy-tailed? only when workers differ? only when queues form early?); sensitivity to parameters (rank stability under ±30%); the upper bound any strategy could achieve (oracle); regressions over time.
- **Cannot answer:** absolute latency or throughput on any hardware; whether the real engine's batch scaling, preemption, prefix caching, chunked prefill or speculative decoding behave like the model; real variance structure (heavy tails, GC and thermal effects); real GPU metrics (utilisation semantics differ by engine/driver); multi-gateway effects.
- **Calibration story:** every parameter has provenance in a versioned file; fitted to Option B/C data where it exists, otherwise labelled "assumed"; the report lists reproduced and non-reproduced behaviours; the parameter hash is frozen at the predictions freeze.
- **Risk of tuning to your own simulator** (the central risk of this phase): the strategies are designed by the same mind that wrote the simulator, and any weight or estimator can be adjusted until the simulator is pleased. Guards: predictions committed first (D25); held-out worlds, workloads and seeds (D23); at most one tuning pass on a tuning set; negative controls and a placebo; rank stability under parameter perturbation; an oracle bound; a blind workload and world variant from the verifier; simulator parameters fixed by calibration or declared assumptions, not by results; the claim sentence form (Outcome); refutations reported. What remains unguarded: a systematic error shared by the simulator and the strategies (both assume batching shape X); only real data (B, C) can expose it, which is why B is in scope and C is gated.
- **Cost:** moderate engineering (PR E, F); free to run; unlimited repeats.

### (b) A real engine on the Mac behind the worker, one or two data points (Option B)

- **What:** llama.cpp `llama-server` (continuous batching with `--parallel N` slots, `--ctx-size` as the KV budget, `/slots` and `/metrics` endpoints), or Ollama (`OLLAMA_NUM_PARALLEL`, fewer metrics), or MLX `mlx_lm.server` (limited batching); a small quantised model (a 1-3 B model for speed, a 7-8 B Q4 as the realistic point) on the project machine (documented elsewhere as an Apple M5 Pro). Preferred: **llama.cpp**, because its slot and KV behaviour is explicit and queryable.
- **Data to collect (script `scripts/calibrate-llamacpp.sh` plus a small Go or shell client, no model files committed):** prefill latency versus prompt length (64 to 8k tokens) at batch 1; decode inter-token latency and aggregate tokens/s versus concurrent streams (1, 2, 4, 8, 16, up to the slot count); behaviour when slots/KV are exhausted (queueing, rejection, latency step); output length distribution versus `max_tokens` for a fixed prompt set; coefficient of variation of TTFT and inter-token latency at fixed load over 10 minutes; thermal throttling check (first versus last minute). Record engine version, model, quantisation, flags, macOS version, power state (`caffeinate`, plugged in).
- **Answers:** whether the simulator's *shapes* (step time linear in batch? prefill cost per token? KV cliff?) are in the right family; the order of magnitude of the prefill-to-decode cost ratio (the number that decides `input_weight`, H5); a realistic noise level; the real `/metrics` vocabulary of a continuous-batching engine (input to a future backend, Phase 13). A second data point (a different model size or quantisation) shows whether the ratios move.
- **Cannot answer:** CUDA/vLLM batch scaling (Metal's saturation curve and memory bandwidth differ), GPU utilisation/memory signals, heterogeneous fleets, multi-GPU; and **running several engines on one Mac is not a cluster**: they share memory bandwidth, so scheduler experiments across "N Mac workers" are confounded. Use it for calibration of one worker's behaviour, not for scheduler comparison. A small end-to-end smoke (gateway in front of one llama-server through a throw-away adapter) is optional and proves nothing about scheduling.
- **Cost:** about a day; no money.

### (c) A short rented GPU session (Option C, gated by the user)

- **Cost range (rough, from general knowledge, to be re-checked at booking time; the repository cannot confirm prices):** a single mid-range GPU (24 GB class, e.g. L4/A10G/RTX 4090) roughly 0.3-1.2 USD/hour; a single A100/H100-class 80 GB roughly 1.5-4 USD/hour on-demand or marketplace. A session of 3-5 hours including setup and model download: **about 5-25 USD** on a 24 GB card, **about 10-40 USD** on an 80 GB card, plus storage/egress pennies. Two small GPUs for a heterogeneous pair: roughly double.
- **Data to collect (vLLM, one 7-8 B model, plus a second size if time allows):** TTFT versus prompt length at batch 1; inter-token latency and aggregate tokens/s versus running batch (1 to 64+); KV cache size in tokens (`num_gpu_blocks`), scheduler behaviour at saturation (waiting-queue growth, preemption), `gpu_cache_usage_perc`, `num_requests_running/waiting` from vLLM's `/metrics`; GPU utilisation and memory as seen by `nvidia-smi` for the same runs (to learn whether utilisation saturates, H8); output-length distribution on a realistic prompt set; noise (CV) at fixed load; and **if the session allows**, two vLLM instances (different `--max-num-seqs` or `--gpu-memory-utilization`, or two GPUs) behind the ServerFlow gateway with a thin `Backend` adapter, running the **held-out** workload against `round-robin`, `least-active`, `least-work`, `latency-aware`: the only real test of the headline claim. This overlaps Phase 13 (a real vLLM pool and backend) and should share the session, not duplicate it.
- **Answers:** whether the simulator's calibrated shapes hold on CUDA/vLLM; whether the strategy ranking replicates at least once on hardware; real GPU signal semantics (D8).
- **Cannot answer:** fleets of tens of GPUs, multi-tenant long-run behaviour, production traffic, cluster autoscaling, other engines/hardware generations; one short session is a data point, not a study.

### Recommendation

1. **Do (a) in full** (PR E and F): without it there is no honest experiment.
2. **Do (b) before the freeze** (PR H): it costs a day and removes the biggest assumption (the shape and ratios), turning "assumed" parameters into "measured on one engine".
3. **Gate (c) behind the user** (PR K), scheduled after PR J and combined with Phase 13: spend one short session only if the user wants a claim beyond "simulator-validated". Until it happens, every document, dashboard note and PR text keeps the label *simulator-validated, not hardware-validated*, and the default strategy does not change.

## Risks

- **Tuning to the simulator** (above): the dominant risk; guarded procedurally (D25, D26, D28), not by good intentions. If the guards are skipped the results document must say so and the claims are void.
- **A learned signal exiles or floods a worker.** Mitigated by decay to the fleet prior, cold-start rules, bounded exile property (I6), a half-open probe test, and H9; residual: interactions with other gateways' views.
- **Capacity estimate is wrong in a regime** (batched engines saturate; idle workers; mixed token units). The decayed-peak rule is a compromise; the prediction-error histogram makes the error visible; H4-H6 are exactly the predictions that expect trouble.
- **Overlay v2 miscounts** (clock-domain arithmetic, bucket boundaries, a history gap) and starts refusing or over-admitting. It is opt-in, falls back to `max` on missing history, has a floor of local in-flight, a naive-reference model check, and the same function guards `AtCapacity` and `freeSlots`. Residual: other gateways' load.
- **Hand-off distortion** (D14): under queueing the strategy is bypassed; measured by H10; a quality-aware hand-off is deferred.
- **Estimator bias and abuse:** `max_tokens` overstates work; a tenant can inflate its estimate within `max_tokens_limit`; dense text is under-estimated (ADR-015). Bounded and measured (D16), not fixed.
- **Hot-path cost and lock hold time** grow with workers (D18): benchmarks gate, with the fallback of moving slow terms to refresh time.
- **Config surface growth:** twelve new keys. Defaults inert, validated only when used, documented once; if the weights prove unnecessary after J, the ADR may deprecate them before anyone depends on them.
- **Scope creep:** worker-reported TTFT/KV usage, learned output length, progress credit for in-flight work and quality-aware hand-off are all tempting; each is a named follow-up with the evidence that would justify it, not part of this phase.
- **Honest-labelling drift:** results quoted without the scope sentence. A docs test checks the label in `phase-14-results.md` and the operations guide.
- **Flaky timing tests** (real-time sim, heartbeats, cool-downs): fake clocks wherever logic allows, generous bounds elsewhere, `-count=10` under load, `caffeinate` for benchmark runs; the DES carries the matrix so real-time cells are few.
- **Time cost:** this is the largest scheduler change so far (eleven PRs). The cut line if time is short: A-D plus E (simulator) deliver the strategies and an honest way to study them; F-J deliver the evidence; K and L are optional.

### What cannot be verified on this machine

Anything on a GPU: real batching/KV/preemption behaviour, `gpu_utilization` semantics, vLLM metric vocabulary, CUDA noise, heterogeneous real fleets, and multi-gateway operation. Mac engine data (Option B) is evidence about one engine on one machine. Any claim not run is stated as such in the results document and the PR.
